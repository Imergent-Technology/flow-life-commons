# ADR 0031: Production transactional mail uses authenticated SMTP

- **Status:** Accepted
- **Date:** 2026-09-28
- **Supersedes:** none
- **Superseded by:** none
- **Refines:** [ADR 0010](0010-database-queue-redis-ready.md) (no queue worker is introduced for mail), [ADR 0024](0024-privileged-operator-administration.md) (delivery semantics are unchanged, not reopened)

## Context

Production (v0.1.1, live since 2026-09-22) runs `MAIL_MAILER=log`: an invitation or password-reset message is written to the application log, not delivered. That is a deliberate deferral, not a defect — [production-readiness.md, section 5](../runbooks/production-readiness.md) records why. A local PHP `mail()` test on 2026-09-21 delivered, but unsigned and DMARC-misaligned (SPF passed only for the host's own envelope sender; no DKIM signature), so it was explicitly rejected as a production transport. Flow Life's mail topology — which provider, which sending identity — is an organizational decision that had not been made.

A design review of the repository (2026-09-28) established what already exists and is already correct, and is not reopened here:

- Both Identity mail adapters ([`MailInvitationNotifier`](../../apps/platform/app/Modules/Identity/Infrastructure/Mail/MailInvitationNotifier.php), [`MailPasswordResetNotifier`](../../apps/platform/app/Modules/Identity/Infrastructure/Mail/MailPasswordResetNotifier.php)) send through Laravel's ordinary mail system and name no provider — the transport is entirely an environment concern.
- Delivery is synchronous and **not queued**, on purpose: a queued job would persist the raw invitation/reset token, which the design forbids. Delivery runs after the issuing transaction commits, never inside it. A delivery failure does not roll back the committed state; it is logged (never the token) and audited (`invitation.delivery_failed`), and the remedy is `ReissueInvitation` or, for a reset, asking again after the throttle.
- An **email**-channel invitation's acceptance is treated as evidence the holder controls the mailbox (`InvitationChannel::provesMailbox()`); an **operator**-handed one is not. This is decided at issue time and is independent of which transport eventually carries the message.
- `security:production-check` (`ProductionReadiness`) already refused the one transport actually measured and found wanting (`sendmail`), and already reports outbound mail's deliverability as permanently **open** until a human records real evidence — SPF alignment, DKIM signing, a DMARC pass, inbox placement — because no reading of configuration can establish those facts.

What remained undecided was the shape of the eventual real transport, and whether the existing fail-closed posture covered it precisely enough. It did not: the readiness check blocked `sendmail` by name only, so an unreviewed future transport, a typo, or the test-only `array` transport would each have passed as "not sendmail" if set in a production environment.

## Decision

**Production transactional delivery uses authenticated SMTP through a transactional mail provider**, via Laravel's stock `smtp` mailer (`config/mail.php`). No custom transport code is introduced: Symfony Mailer (the framework's mail layer) already supports everything this requires — a `require_tls` option that makes STARTTLS mandatory rather than opportunistic, and a `timeout` that bounds the synchronous connection — as plain configuration-array keys.

- **The provider is not chosen here and is not compiled into Identity.** Laravel's `smtp` mailer takes a host, port and credentials from the environment; switching providers is an environment change, not a code change. Choosing one is an operational decision (below).
- **The sending identity is delegated to a dedicated Commons-controlled subdomain**, not the root domain. `flowlifeglobal.org` already carries its own SPF, DMARC and MX serving `info@flowlifeglobal.org` (a GoDaddy-hosted mailbox, unrelated to Commons); authenticating a transactional provider against the root domain would either fight that record or risk someone weakening it later to make Commons' mail work. A subdomain (exact label an operational decision, below) gets its own SPF/DKIM/DMARC, entirely additive, and keeps WordPress's mail identity untouched — extending the same trust-domain separation [ADR 0004](0004-wordpress-adapter-not-authority.md) already holds between WordPress and Commons into mail sending identity.
- **Invitation and reset delivery stay synchronous, at current scale.** No queue is introduced. Volume is one or a few operators issuing/reissuing invitations and the occasional password reset — not a volume synchronous SMTP cannot absorb — and a queued message would have to either persist the raw token (forbidden) or be dispatched from already-committed state with the token re-derived, which does not exist and is not being built speculatively. [ADR 0010](0010-database-queue-redis-ready.md)'s queue remains unused by mail.
- **Raw credential-bearing tokens are never queued or persisted**, unchanged from today: neither Mailable implements `ShouldQueue`, and nothing in this decision adds a job, an outbox or a durable payload that could carry one.
- **Identity's post-commit failure/reissue behaviour is preserved exactly.** `DeliverInvitation`, `RequestPasswordReset`, both notifiers, both Mailables and `InvitationChannel` are unchanged by this ADR — transport selection happens entirely below them, in `config/mail.php` and the environment.
- **`security:production-check` now fails closed on an explicit allowlist**, not a blocklist: only `log` (the documented deferral) and `smtp` (this decision's transport) are accepted in production at all. `sendmail` (measured and rejected), `array` (a test-only transport) and anything not on the allowlist — an HTTP-API provider, `failover`, `roundrobin`, a typo — each fail the deployment, by not being on it. Adopting an HTTP-API transport later is meant to be an intentional, reviewed change to that allowlist, not a value someone can set ahead of it.
- **When `smtp` is configured, its shape is checked as far as configuration alone can honestly speak to it**: a real host and port (not Mailpit's), real credentials, a real sender identity, TLS that is mandatory rather than merely offered (`require_tls`, or implicit TLS on port 465 — because Symfony Mailer's default on the `smtp` scheme is *opportunistic* STARTTLS, and would otherwise send in plaintext if a server ever stopped advertising it), certificate verification left enabled, and a positive, bounded timeout (≤30s — there is no queue absorbing a hang, so this is how long a real person's request can block on a stalled connection). **None of this can establish SPF alignment, DKIM signing, a DMARC pass or inbox placement.** Those remain `deferred()`'s job: reported open on every run, regardless of how correctly `smtp` is shaped, until a human records a real send's outcome in [production-readiness.md, section 5](../runbooks/production-readiness.md).
- **Production stays on `MAIL_MAILER=log` until that evidence exists.** This ADR records the target architecture and hardens the code that will carry it; it does not itself switch production, choose a provider, touch DNS or claim mail has been verified.

## Consequences

- Adopting a provider becomes an environment change on the host (`shared/.env`) plus DNS records on the new subdomain — no release, no code change, no Identity module touched.
- A misconfigured or half-configured `smtp` deployment fails `security:production-check` structurally (empty host, Mailpit's own host/port, missing credentials, a placeholder sender address, TLS left optional, an unset or excessive timeout) before anyone has to notice it by watching invitations silently vanish.
- The one thing configuration can never prove — real deliverability — stays explicitly, permanently open until a human records it, exactly as it already did for `log`. A structurally perfect `smtp` configuration is necessary and still not sufficient.
- A request that invites someone or handles a password reset now has a hard ceiling (default 10s, enforced ≤30s) on how long it can block waiting on SMTP, where previously an unset timeout fell through to PHP's own `default_socket_timeout` ini — a fact this application did not control and had not stated.
- Portability to a future VPS is unaffected: `smtp` with environment-supplied host/credentials works anywhere Laravel runs; nothing here is cPanel-specific.

## Alternatives considered

- **A provider's HTTP API instead of SMTP.** Rejected for now: it would add a Composer dependency and a new failure/timeout surface for no benefit here — the confirmed-open SMTP ports (25/465/587) and Laravel's zero-dependency `smtp` mailer (already exercised in development against Mailpit) make SMTP the smaller footprint. Revisiting this is exactly the kind of change the allowlist is built to make deliberate rather than accidental.
- **Authenticating against the root domain (`flowlifeglobal.org`) instead of a subdomain.** Rejected: the root domain's SPF/DMARC/MX already serve `info@flowlifeglobal.org`; layering a transactional provider onto it risks weakening that mailbox's own deliverability, a risk a dedicated subdomain avoids entirely by being additive.
- **cPanel/hosting-account mail as the transport.** Rejected: the one thing actually tested (`sendmail`, PHP's own local relay) delivered unsigned and DMARC-misaligned, and the account's DKIM configurability could not even be confirmed (the cPanel Email Deliverability tool is not exposed on this account; the `default._domainkey` DNS probe found nothing, which does not prove absence but does not establish presence either).
- **Deriving readiness "closed" from `MAIL_MAILER=smtp` alone.** Rejected, and already rejected once before this ADR: an authenticated-*looking* transport (a real host, real credentials) reports the same configured shape whether or not it has ever been verified. The deferred item can never close from configuration; only a recorded real send can.
- **Closing the production-readiness mail deferral now.** Rejected: no real provider, DNS or verified send exists yet. This ADR prepares the code; activation is a separate, later step with its own evidence.
- **Blocking only `sendmail` by name, as the check did before this ADR.** Rejected: it passes anything merely by not being `sendmail`, including a test-only `array` transport or an unreviewed future one. An explicit allowlist is the fail-closed version of the same intent.
- **A queue-backed outbox for mail.** Not built: current volume does not need it, [ADR 0010](0010-database-queue-redis-ready.md) already anticipated deferring this until a real job exists, and a durable payload for a message carrying a one-time secret is exactly what the current no-storage design forbids.
