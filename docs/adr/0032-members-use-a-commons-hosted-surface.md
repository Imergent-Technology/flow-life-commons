# ADR 0032: Members use a Commons-hosted surface

- **Status:** Accepted (implemented for the Member foundation, Work Packages 1–5; further Member expansion parked — see [member access](../architecture/member-access.md))
- **Date:** 2026-09-28
- **Supersedes:** none
- **Superseded by:** none
- **Refines:** [ADR 0004](0004-wordpress-adapter-not-authority.md) (context only — the core decision, that WordPress is never the authority, is unchanged and reinforced), [ADR 0016](0016-guardian-console-same-origin-session-authentication.md) (extended to a second authenticated surface on the same origin, without changing the cookie model it decided)

## Context

A design gate (2026-09-28) inspected the current repository — Identity, Access, Membership, the Guardian Console, the WordPress companion, and the trust-boundary docs — against the unresolved question of how ordinary Members, and later Volunteers, should reach Commons. Two facts the gate found change what ADR 0004's context assumed at the time:

- **A password-only authenticated session is already a first-class state**, not a gap to fill. `SecondFactorRequirement`/`ConsoleMultiFactorPolicy` (ADR 0023) already challenge for MFA only when the signed-in Account currently holds `console.access`; an Account without it authenticates with a password alone, and `EndSessionWithoutSecondFactor` already force-ends such a session the moment the Account gains that capability. Nothing new needs building for a lower-privilege authenticated tier to exist safely.
- **Membership access is a query, not an identity fact.** ADR 0028 derives active membership from grants at query time and explicitly reserves the mechanism (an Access-defined port, Membership-implemented) for a future membership-derived capability. It does not require a "Member" identity, role or session shape distinct from an ordinary Account.

Given both, the cost of a Commons-hosted member surface is small — mostly new endpoints and a route area in the existing Console frontend — while the cost of delivering the same experience *inside* WordPress is building a working subset of OAuth (ADR 0018's delegated flow) before a single member screen can ship. ADR 0004's context (2026-09-19) assumed member functionality would be "presented largely through WordPress"; that assumption is now revised, not because ADR 0004's decision was wrong, but because building on the session model ADR 0016 already proved is materially cheaper than building delegation first.

## Decision

**Commons hosts the authenticated Member/self-service surface. WordPress links to it and holds no authenticated Commons authority.**

- **Same origin, same session model.** The member surface is served from `commons.flowlifeglobal.org`, using the existing `__Host-` prefixed, host-only session cookie, the existing database-backed sessions, and the existing CSRF handling (ADR 0016). **Nothing about the cookie changes**: no `Domain` attribute is added, no parent-domain (`.flowlifeglobal.org`) cookie is introduced, and WordPress continues to neither receive nor be able to shadow it.
- **No iframe.** The production CSP's `frame-ancestors 'none'` (ADR 0026) already forbids WordPress from framing Commons, and this decision does not relax it.
- **WordPress's role in this phase is a link.** A "Member sign in" or "My account" link/button pointing at Commons requires no plugin code and no companion feature. WordPress renders no authenticated member data, receives no person-specific Commons data, holds no Commons credential, and maps no WordPress user to a Commons Person. `apps/wordpress-companion` stays the skeleton it is today; the existing boundary check (`scripts/tests/wordpress-boundary.php`) is expected to keep passing unchanged.
- **No authenticated member content is ever cached by Sucuri or any edge**, because none exists on the WordPress side to cache. Every Commons API response already carries `Cache-Control: no-store`.
- **Guardian Console access is unaffected and stays separately authorized.** `console.access` remains its own capability, checked exactly as today; nothing about this decision widens who may reach `/admin/*` or the Console shell.
- **The same frontend application may host both**, as a distinct `MemberShell` and a `/my/*` route area alongside the existing Console shell and its `/admin/*` area, without either becoming the other. A frontend-side import boundary (a guardrail test, in the pattern already used elsewhere in this codebase) keeps member-area code from depending on Console/admin code and vice versa. This is an implementation choice, not a frozen design; a future work package may still find a separate bundle or a separate origin worth the extra cost (see below).
- **Members are not required to enrol a second factor.** This makes explicit, as a product decision, what the existing mechanism already defaults to: `SecondFactorRequirement` challenges an Account that already has an active authenticator, and asks a Console-privileged Account (`console.access`) to enrol one, but asks nothing extra of an ordinary Member. Promotion into `console.access` continues to force-terminate a password-only session (`EndSessionWithoutSecondFactor`) and requires the stronger flow before the Account can use its new privilege. Voluntary MFA for a Member who wants it is deferred, not rejected.
- **Reaching `/my/` is not evidence of active membership.** It is an authenticated self-service area for any Account that has no higher-privilege destination — an active Member, a lapsed Member, or a future Account type with no membership at all. `GET /my/membership` (when built) truthfully answers "none", "active, ends `<date>`" or "active, open-ended" for whoever is asking about themselves; a Member-*only* resource, when one is needed, is gated by an actual capability derived from current membership state (ADR 0028's reserved mechanism), never by the mere fact of reaching this route area.
- **A generic Identity capability — inviting an existing Person who has no Account — is accepted in direction.** Membership can already register a Person with no Account (`RegisterPerson`, ADR 0028); today there is no way to give that Person an Account afterwards, because `InviteAccount` always creates a new Person. This gap is Identity's to close (a Person-scoped invitation path, not a Membership-specific one), and is scoped as its own work package. **When** any legacy or existing Person is actually invited is a separate, later operational decision — production mail must be active (ADR 0031) and legacy records reviewed first — and is not decided here.
- **Credential and invitation presentation becomes neutral Flow Life Commons presentation**, not Guardian-Console-specific. `/login`, `/accept-invitation`, `/forgot-password` and `/reset-password`, and the invitation/reset mail copy, currently say "Guardian Console" throughout; they must stop assuming every recipient is an operator. Exact wording is a later, smaller decision (see [member access](../architecture/member-access.md)), not made here.

## Consequences

- Building the first member screen costs a handful of backend endpoints and one new frontend shell, on infrastructure that already exists and is already hardened — not a new identity provider, not a new host, not a new session model.
- A fully compromised WordPress installation, under this decision, can phish or deface but cannot read, forge or replay anything that reaches Commons: it holds nothing Commons-issued. This is a direct consequence of building nothing delegated yet (see ADR 0033).
- The credential pages and mail copy need rewording before any real Member uses them; shipping them unchanged while onboarding Members would be confusing, not insecure.
- The frontend gains an import-boundary obligation (member code must not reach admin code) that did not exist when the Console was the only authenticated area.
- Deferred, and named here so the trigger is not lost: if the member area ever needs to render user-generated or otherwise untrusted content (posts, rich profiles, messaging), the same-origin-with-the-Console arrangement is worth reconsidering — an XSS there would ride whatever session is active, Guardian sessions included. Nothing here designs that; it is the stated condition for revisiting it.

## Alternatives considered

- **Deliver the member experience inside WordPress via delegated access (ADR 0018).** Rejected for now: it requires building a working authorization-code flow before a single member screen can ship, and it puts live human bearer authority inside a system explicitly outside the security perimeter (ADR 0004). Not rejected forever — see ADR 0033.
- **A separate origin for the member surface** (for example `members.flowlifeglobal.org`), isolated from the Guardian Console. Gives stronger isolation against a member-area XSS reaching a Guardian session, at the cost of a second host, a second session boundary, and trusted-host reconfiguration. Deferred with an explicit trigger above, not chosen now, because nothing in the current member surface (self-service on one's own account and membership data) creates that risk today.
- **Iframing Commons content inside WordPress pages.** Rejected outright: blocked by the existing `frame-ancestors 'none'` policy (ADR 0026), and framing an authenticated surface inside a lower-trust origin is the wrong direction regardless.
