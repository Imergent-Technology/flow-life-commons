# Data ownership

## Principles

1. **The platform database is the system of record** for organizational data. Nothing of record lives in WordPress tables, options or user meta, in browser storage, or in caches.
2. **A module owns its tables.** Only that module's code writes to them. Other modules read through the owning module's `Application` layer, not by querying its tables or models directly (see [module map](module-map.md)).
3. **Identifiers** for platform aggregates are application-generated ULIDs ([ADR 0006](../adr/0006-ulid-identifiers.md)); they are created in code, not by the database, so they can be known before insert and behave the same on every engine.
4. **Timestamps** are persisted in UTC. Presentation converts to a local zone at the edge.
5. **Caches are never authoritative.** Anything in a cache must be reconstructible from the database, and correctness must not depend on a cache hit.
6. **Schema stays portable** between MariaDB and PostgreSQL ([ADR 0005](../adr/0005-mariadb-with-postgresql-portability.md)): no database enums, triggers, stored procedures, proprietary SQL or generated columns without an ADR.

## External copies

Data mirrored to other systems (for example a WordPress user display name) is a **projection** of platform data. The platform wins on any disagreement, and projections must be rebuildable from the platform. External identities are *linked to* platform identities, never the other way round.

## Current state

Platform-owned tables exist for Identity, Access, Audit, Membership, Crm, Discussions, Resources and Relationships ([module map](module-map.md)):

- **Identity**: `people`, `accounts`, `account_invitations`, `sessions`, `account_totp_factors`, `account_recovery_codes`, `password_reset_tokens`.
- **Access**: `role_assignments` and `sourced_role_grants` (ADR 0038, WP2A). Independent assignments stay in `role_assignments`. `sourced_role_grants` holds a role an authorized operator granted because of one source instance (`source_type`, `source_id`, no foreign key to the source) with a `RESTRICT` key to `people`. The `Authorizer` unions both. Relationship lifecycle does not create these grants yet: `NoRelationshipGrants` remains the withdrawal adapter until WP2B replaces it with atomic withdrawal on inactivation and deletion. The release that renames stored `guardian` role keys to `guardian-full` is `restore-required` (ADR 0027): a code-only rollback would leave those keys unknown and would remove that bundle.
- **Audit**: `security_events`.
- **Crm**: `contact_profiles`, `contact_methods`, `contact_tags`, `contact_tag_assignments` (ADR 0034). Keyed by `person_id` with `RESTRICT` cross-module foreign keys; `*_by_account_id` columns are provenance with none. Accepted design of ADR 0038 (WP3), not built: `contact_methods.updated_by_account_id`, the Account that last created or changed each contact method, `NULL` for rows from before it. Sparse: a Person has a `contact_profiles` row only once there is CRM data to hold, and it doubles as the per-Person write lock. No Account, role, Membership or status column.
- **Discussions** ([ADR 0035](../adr/0035-guardian-discussions-are-durable-asynchronous-threads.md); backend built): `discussions` and `discussion_messages`. Authors, editors and resolvers are Person ids with no foreign key (provenance); the only foreign key is a message's discussion, within the module. A removed message keeps its place and author but its text is set to NULL, not retained elsewhere; edits overwrite with no history. Not `security_events`.
- **Membership**: `membership_grants`. Backend, an operator-only `/admin/members` HTTP surface (Work Package 5), and a Guardian Console administration UI (Work Package 6).
- **Relationships** ([ADR 0038](../adr/0038-organizational-relationships-and-resource-viewing-authority.md); WP1 built): `person_relationships`, `person_relationship_status_changes`, `person_relationship_field_values` and `person_relationship_role_provisions`. One ongoing relationship of each type per Person (`unique(person_id, relationship_type)`, named `person_relationships_person_type_unique`), `RESTRICT` keys to `people` and within the module, provenance as Person ids with no foreign key, typed key-value metadata as `text` (no JSON column), and no contact, name or Account column. Writes of an existing row compare `relationship_id` and `revision`. Permanent deletion removes the relationship, its metadata, history and any provisioning decision, and leaves one `relationship.deleted` security event. The decision table is unused until WP2B. Sourced-grant withdrawal is still `NoRelationshipGrants`: deletion calls it and inactivation does not. WP2A added `sourced_role_grants` and the Authorizer union in Access, and did not call them from Relationships. Those grants must not become live through a relationship until WP2B replaces the adapter with atomic withdrawal on both inactivation and deletion. Contact data stays CRM's, and Membership stays Membership's.
- **Resources** ([ADR 0037](../adr/0037-resources-are-audience-targeted-packs-of-cards.md); built; a development-only demo seeder writes through its use cases, and its one direct write repairs the provenance of its own rows): `resource_categories`, `resource_packs`, `resource_pack_audiences`, `resource_cards`, `resource_card_audiences`, `resource_assets`. Every foreign key is within the module and `RESTRICT`; deletion is an explicit use case. Creators, editors and uploaders are Person ids with no foreign key. Rich content is stored as a validated document (canonical JSON text in a `mediumText` column, not a database `json` type, as measured on both engines), never as HTML. Positions are not unique (`(position, id)` is the order) and creators and editors are Person ids with no foreign key. Permanent deletion of a Pack or Card is recorded in `security_events` (who and which ids, never the deleted content), and nothing deleted is retained in Resources. Resources stores which audiences content targets and **no relationship fact**: whether a Person is a Member, Volunteer or anything else is asked of that relationship's owner ([ADR 0036](../adr/0036-business-relationships-are-independent-and-not-access-roles.md)). **File contents are data of record outside the database**: each File Card's file lives on the private `resources` disk, `storage/app/private/resources`, which on the production host is in the release-shared `shared/storage` ([ADR 0027](../adr/0027-release-and-deployment-model.md)), named by its asset's id; `resource_assets` holds its metadata (sanitised original name, detected media type, size, SHA-256, uploader as a Person id with no foreign key) and never a path. A File Card owns exactly one asset (`resource_cards.asset_id` is unique, a `RESTRICT` foreign key), and no asset is shared or kept after it is replaced or deleted. The database and the files must be backed up and restored together ([backup and restore](../runbooks/backup-and-restore.md#resource-files)). A file is written before its row commits and removed only after the row's deletion commits, so a failure leaves an unreferenced file (never a row without a file by design), which `resources:assets:prune` removes.

Platform aggregates use application-generated ULID primary keys, per the principle above. Framework infrastructure created by Laravel's stock migrations — `migrations`, `cache`, `cache_locks`, `jobs`, `job_batches`, `failed_jobs` — keeps Laravel's default keys because it is not platform aggregate data. There is deliberately no `users` table: Identity's `people`/`accounts` split is the human registry ([authorization model](../security/authorization-model.md)).

## Answered by the Identity and Access design gate

- **Table naming:** unprefixed. Module ownership is recorded in the [module map](module-map.md) and the module's own documentation, not encoded in table names.
- **Cross-module foreign keys:** permitted, deliberately, where the reference is a fundamental invariant — with `RESTRICT`, never `CASCADE`, and never for provenance or audit references. Write ownership, code dependency and referential integrity are three independent concerns ([ADR 0021](../adr/0021-cross-module-referential-integrity.md)).
- **Where the audit trail lives:** a small `Audit` module owning an append-only `security_events` table with no foreign keys, so it outlives its subjects and never blocks an operation ([ADR 0019](../adr/0019-security-event-auditing-seam.md)).

## Membership (ADR 0028, ADR 0029)

- **`Membership` owns one table, `membership_grants`**, holding time-bounded grants of membership access. Whether a Person is a member *now* is **derived from those rows at query time**, not stored: there is no status column and no expiry job.
- **Grants are a non-deleting history with one-way revocation.** Nothing but `revoked_at`/`revoked_by_account_id` is ever changed, and no row is deleted.
- **`person_id` carries a cross-module foreign key with `RESTRICT`**; `granted_by_account_id` and `revoked_by_account_id` are provenance and carry none — the calls [ADR 0021](../adr/0021-cross-module-referential-integrity.md) already defines. Membership's migrations therefore run after Identity's.
- **Payment facts stay out of the schema.** Amount, currency, payment method, provider status, subscription mechanics, campaign fields and receipt state belong to the commerce provider, never to `membership_grants` ([ADR 0029](../adr/0029-commerce-providers-own-payment-facts.md)). Provider identity may appear only as provenance, in `source`/`source_reference`, which Membership never parses and which carry no uniqueness constraint.
- **Membership access is never represented solely by a role assignment**, because a role assignment does not expire and membership lapses by the passage of time ([ADR 0028](../adr/0028-membership-grants-derived-at-query-time.md)).
