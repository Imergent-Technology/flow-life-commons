# G6 WP6B: dependency advisory triage (G6-D26)

- **What this is.** One bounded, read-only assessment of the nine Composer advisories that `./flow audit` reported on 2026-11-23 (**eight affecting runtime packages and one, `symfony/yaml`, development-only**), found during the G6 closeout. It is **not** a dependency audit, a remediation or a new work package. **No dependency was changed** (`composer.lock` is untouched) and nothing was deployed. The register row is [G6-D26](debt-register.md).
- **How it was found.** The weekly `Security audit` workflow on `main` has failed on every run since 2026-11-02 (last success 2026-10-26); nothing had recorded it. `./flow audit` is outside `./flow check` by design ([testing](../../development/testing.md)), so no gate showed it. It was run here read-only in the development container.
- **Method and limits.** Advisory text from the publishers (GitHub advisories and symfony.com), read on 2026-11-23. Applicability from a source and configuration search of this repository at `0fce508`. The advisories' own preconditions are quoted closely; **"not applicable" below means the precondition is absent, with the evidence named, and "not investigated" means exactly that.** The assessment cannot see the production host; where a precondition depends on it, that is said.
- **Production versus development.** In `composer.lock`, `symfony/yaml` is in `packages-dev` (it is in `require-dev`), and the release builder installs with `composer install --no-dev` ([`release.sh`](../../../scripts/lib/release.sh)). The other five are in `packages` (runtime). The lock **tagged at `v0.3.0`** carries the **same versions** of all six packages, so a release built from that tag had the same runtime versions. That is a statement about the tagged lockfile; production itself was **not accessed**, and nothing here asserts what is installed on the host.
- **Patched releases.** For each package a same-major patched release exists inside the existing constraints (`laravel/framework ^13.17`): `laravel/framework` 13.40.0 or later; `symfony/http-foundation`, `http-kernel`, `routing` and `yaml` 7.4.23; `symfony/mime` 7.4.22. A `composer update --dry-run` (nothing written) resolved `laravel/framework` 13.43.0 and Symfony 7.4.22 to 7.4.23, but its broad form (with dependencies) listed 53 updates, including a major bump of `brick/math`; a narrower, package-by-package update was **not** tried. That is the update package's work.

## What is established and what is not

- **Established (from the lockfiles, the advisories and the source):** the nine advisories (eight on runtime packages, one development-only), their locked versions, which package is runtime or development, that the tagged `v0.3.0` lock carries the same versions, that patched same-major releases exist, and that the specific vulnerable features named in advisories 1, 2, 3, 6, 8 and 9 (and the mail-parameter path of 7, and the link construction of 5) are **absent** from this application's code and configuration.
- **Not established:** the production host's layout for advisories 4 and 5 (script name, any proxy or CDN); the behaviour of direct `/index.php/...` requests; the actual installed versions on the host; whether a narrow package-by-package update resolves cleanly; the build impact of the npm development findings. None was investigated, by the scope of this triage.
- **Confirmed non-applicability is not a claim of safety.** It says the advisory's precondition is not present in this repository today. A later change (a proxy or CDN in front of production, a custom mail header or attachment, YAML input, host-restricted routes) would change it, which is why the revisit trigger below includes them.

## Owner ruling on G6-D26 (PR #36 review, 2026-11-23)

The per-advisory severities in the table above are this triage's **proposals**, and the proposal for the whole was LOW. **The owner ruled otherwise:**

1. **Severity: MEDIUM, application exposure not demonstrated.** Not LOW, because the production host's path and front-controller behaviour and the installed dependencies were not independently verified, so the uncertainty is real.
2. **Accepted temporarily under DP4, for the purpose of closing G6 only.** Rationale: the bounded source assessment found no confirmed reachable vulnerable path; the High-rated `symfony/yaml` advisory is in a development-only dependency; the application does not use several of the affected features; the production host and its installed dependencies were not verified; G6 completion authorizes no deployment; and compatible patched releases exist.
3. **This acceptance does not authorize using the existing lockfile for the next production deployment.**
4. **Remediation is required before the next release,** by a **separate, prioritized dependency-security package** that: updates the affected dependencies (package by package, within the existing constraints, clearing the route cache after the routing update); verifies compatibility (the dual-engine gate and the browser gate); **investigates the unresolved path-handling cases** (advisories 4 and 5: the `/index.php…` forms, the host's script-name layout); and **restores a passing runtime dependency audit**. It is not part of WP6B, and WP6B made no lock change.
5. **Revisit trigger:** the next production release (unconditionally); the weekly audit still failing; any new advisory on a runtime package; any proxy, CDN, custom mail header or attachment, YAML input or host-restricted route being added; or G7 exposing more of the HTTP surface.
6. **Release restriction:** the next release stays blocked by its dependency-audit item ([release readiness, item 12](../../runbooks/g10-release-readiness.md)). Any waiver of that requirement needs a **separate, advisory-specific, explicit owner decision**. A green routine CI run does not resolve it.
7. **Operational follow-up, separate and not implemented in WP6B:** the scheduled `Security audit` workflow failed on four consecutive weekly runs with nothing alerting. It should report failures to a monitored destination. No workflow or notification was changed here.
