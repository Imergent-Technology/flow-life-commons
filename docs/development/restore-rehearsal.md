# The local recovery rehearsal

**Status.** G6 WP3c ([contract](../audits/g6/README.md#wp3--data-integrity-upgrade-and-restore-safety)). Slice 1 is the isolated database environment and its safeguards; slice 2.1 adds a PHP execution substrate (a source volume, a preparation step and disposable runners) and passed its first live validation (L1, below). Slice 2.2A, the first half of the recovery cycle (historical baseline, backup, upgrade, and a demonstration of the audited WP3-01 restore defect), and slice 2.2B, the second half (the corrected restore, a sign-in with TOTP on the restored application, and the re-upgrade), passed their first complete live run (L2, [below](#l2-the-live-recovery-rehearsal-passed-2026-11-14): 12 stages, 2026-11-14, synthetic data, one local machine). **That is evidence about this script and the recovery strategy it rehearses, not production recovery readiness:** the production operator procedure is unchanged and the real-host decision stands. Slice 2.2C-1 (a half-failed upgrade, restored from; and a security change made after the backup, reversed by the restore) passed its live run (L3a, [below](#l3a-the-live-half-failed-upgrade-rehearsal-passed-2026-11-16): 15 stages, 2026-11-16, synthetic data, one local machine), after an independent safety review and its remediation. Slice 2.2C-2 (the Resource files: an isolated files volume and container, an archive and a manifest, and the refusal of every unsafe file state) was implemented, independently reviewed twice (Opus 5.5, SAFE FOR L3b each time) and passed its live run (L3b, [below](#l3b-the-live-resource-files-rehearsal-passed-2026-11-17): two lifecycles, 2026-11-17, synthetic data, one local machine; the slice itself is [here](#slice-22c-2-the-resource-files-implemented-l3b-passed-2026-11-17)); the complete database-and-files cycle (slice 2.2C-3) and security reconciliation are not done, **Resource-file recovery is not production-ready**, and WP3c stays open.

**What it is for.** Later slices use it to prove, with synthetic data on a local machine, that the organization can recover v0.3.0 after an unsuccessful upgrade. It never touches production or staging, reads no application `.env`, holds no host credentials and uses no production data. A local rehearsal does not replace the decision on the real host ([contract §9](../audits/g6/README.md#9-release-track-outside-g6)).

**What it is not.** A general restore or backup tool, and not an automatic rollback. No command takes a file, a database name or a statement from the caller. The only things that change the rehearsal database are the application's own migrations, the fixed fixture and marker helper, `reproduce-wp3-01` (which loads the one dump this script took in order to show a defect and is not a restoration), and `restore-historical`, which drops exactly the 34 tables this script names and loads that same dump. None takes an argument. It is deliberately not a `./flow` command: the runbooks state that `./flow` has no `backup` or `restore`.

## Using it

```bash
scripts/rehearsal/restore-rehearsal.sh self-check          # read-only: environment, and the project if one exists
scripts/rehearsal/restore-rehearsal.sh up                  # start the isolated MariaDB 10.11.18 and verify it
scripts/rehearsal/restore-rehearsal.sh cleanup --dry-run   # list exactly what cleanup would remove
scripts/rehearsal/restore-rehearsal.sh cleanup             # remove it
```

Run it from a clean shell. It refuses if any `COMPOSE_*`, `DB_*`, `MYSQL_*`, `MARIADB_*`, `PG*`, `POSTGRES_*`, `APP_*`, `REHEARSAL_*` or `DATABASE_URL` variable, or `DOCKER_HOST`, `DOCKER_CONTEXT` or a Docker TLS variable, is set. It names the variables and never prints their values.

If `up` is interrupted, or an earlier run was never cleaned, the next `up` refuses and says so. Run `cleanup --dry-run`, read the list, then `cleanup`.

**A cleanup that cannot finish says so.** If any rehearsal-labelled object is kept (a foreign container is attached to the network or uses the volume, an object no longer verifies, or a removal fails), `cleanup` removes what it can prove is its own, lists what remains and why, **keeps the state directory** (it holds the run token) and exits 1. Remove the cause yourself, then run plain `cleanup` again: it completes what is left, including when some objects are already gone. `--stale` is not needed for this and should not be used for it.

`cleanup --stale` is needed only when the private state file has been lost, because the run token then cannot be checked: review `cleanup --dry-run --stale` first. Every other identity check still applies to it.

If `compose.env` exists but is malformed, nothing can be checked against it and every command (including `--stale`) refuses without changing anything. The script never edits, discards or rebuilds that file. Move it out of the state directory to a place of your choosing if you want to keep it as evidence (`cp -p` first if you prefer a copy), review `cleanup --dry-run --stale`, then `cleanup --stale`. The script never deletes it; a file left inside the state directory keeps the directory in place (next paragraph).

**The state directory is only removed if it holds nothing else.** When the objects are gone, cleanup removes `compose.env`, `run.lock` and the marker, then the directory. If the directory holds any other entry (a file, a directory, a dotfile, or a symlink where one of those three files should be), cleanup removes **nothing** from it, names the entries, keeps the marker and the run token (so the directory is still one this script recognises, and `up` can use it once `compose.env` is gone), exits 1, and finishes normally on the next `cleanup` after you have dealt with those entries. It never removes what it did not write.

## What it creates

`up` creates one container, one network and one volume (the base database environment), all named in [compose.yaml](../../scripts/rehearsal/compose.yaml) with literal names and the label `io.flowlife.rehearsal=restore-v1`. Slice 2.1 adds, outside Compose, a source volume `flc-rehearsal-restore-src` (created by `prepare`) and short-lived preparation and runner containers (see below); `cleanup` removes all of them.

| Object | Name | Properties |
| --- | --- | --- |
| container | `flc-rehearsal-restore-mariadb` | `mirror.gcr.io/library/mariadb:10.11.18`, no published port, no bind mount, no Docker socket, not privileged |
| network | `flc-rehearsal-restore-db` | `internal: true`: no route to external networks, nothing published to the host; the bridge gateway is a residual (see Limits) |
| volume | `flc-rehearsal-restore-db-data` | plain `local` volume |
| state directory | `~/.local/state/flowlife-restore-rehearsal` (override: `FLC_REHEARSAL_ROOT`) | mode 700, `compose.env` (per-run credentials and run token, mode 600), lock file |

Databases: `flc_rehearsal_app` (the target), `flc_rehearsal_identity` (the sentinel holding the run token). Scratch databases `flc_rehearsal_scratch_1` to `_3` are allowlisted for later slices and not created.

Pulling the image uses the Docker daemon. The database container never gains network egress as a result: the network is internal. Composer dependencies are fetched by `prepare` (slice 2.1, below) in a separate preparation container with no database credentials and no route to this network. The network's isolation is not weakened to make that work.

## Slice 2.1: the PHP execution substrate

**Status.** Implemented, tested against the fake daemon, and validated live once (L1, below: passed on 2026-11-12). It runs no migration and restores nothing: the backup, schema clearing, restore and evidence cycle are slice 2.2. Any further live Docker lifecycle needs the owner's separate authorization.

```bash
scripts/rehearsal/restore-rehearsal.sh prepare                       # after `up`: archive source and install dependencies into a labelled volume
scripts/rehearsal/restore-rehearsal.sh run <historical|current> <name> # one approved command in a disposable PHP runner
scripts/rehearsal/restore-rehearsal.sh probe                         # fixed isolation probe (read-only)
```

**`prepare`.** Archives `apps/platform` from two *verified* commits with `git archive` (no historical worktree): v0.3.0 (`2f385b79a7b83323c6f15a6685ee610ccd85b5bf`, what production runs) and the current `HEAD`, plus the fixed helpers in [`scripts/rehearsal/php/`](../../scripts/rehearsal/php), into the labelled volume `flc-rehearsal-restore-src` (`/var/www/html/{historical,current,harness}`). Composer runs before the harness is copied in, so nothing it ran can have written to the harness. If the historical commit is not in the clone (a shallow clone), `prepare` refuses, names the commit and proposes `git fetch`; it never substitutes another commit. Each tree then gets `composer install --no-dev --no-scripts --no-interaction --no-progress --prefer-dist --optimize-autoloader` (the release build's flags, `scripts/lib/release.sh`) from its own `composer.lock`. Dependency acquisition is the only step with a route out, and it runs in a container with no database credentials that is never attached to the database network. It refuses if the volume already exists; it never adopts one. Uncommitted changes are not archived: `current` means the commit `HEAD` names, which `prepare` prints.

**`run`.** One disposable container from the development image `flowlife-dev/php:8.3` (resolved once to an image ID, launched by that ID, never pulled or built here), on the internal database network only, with the source mounted read-only, a read-only root filesystem, small `tmpfs` mounts for `/tmp` and each tree's `storage` and `bootstrap/cache`, all capabilities dropped, `no-new-privileges`, uid/gid 33, 1 GiB memory, one CPU and 256 processes, no published port, no Docker socket and no bind mount. The container is created, its identity is checked against what Docker reports (name, image ID, labels, user, root filesystem, capabilities, network, mounts, tmpfs, limits), and only then started; it is removed afterwards. The caller supplies a version and a name; the script builds the whole argument vector:

| Name | Runs |
| --- | --- |
| `about`, `migrate:status`, `relationships:check`, `release:show` | `php artisan <name>` |
| `migrate` | `php artisan migrate --force --no-interaction` (default migration path, no override) |
| `resources:assets:prune` | `php artisan resources:assets:prune --dry-run` |
| `helper:db-ping` | the fixed helper `php /var/www/html/harness/db-ping.php` |

Anything else, any extra argument, any other version name, and any caller-chosen option, file, alias or environment is refused before Docker is contacted. Abbreviations (`res:ass:pru`) are refused because only exact names match. The runner's environment is fixed (`APP_ENV=production`, array cache and session, `LOG_CHANNEL=stderr`, database host, name and user) plus `DB_PASSWORD`, which is the application account's synthetic per-run password and the only secret it receives. `APP_KEY` is a fixed placeholder, not a secret: the data is synthetic and nothing leaves the runner. Slice 2.2 may need a per-run key if it exercises encrypted data.

**The launcher.** `dkr` runs docker under `env -i`, so `docker run -e NAME` would not see the password. `launch_docker` instead unsets every variable but `PATH`, `HOME`, `LANG` and `DOCKER_CONFIG` in a subshell, exports `DB_PASSWORD`, and runs `docker create ... -e DB_PASSWORD` (a name, never a value). `env -i NAME=value` is not used because it would put the value in a process argument. Only the runner's `create` goes through it; preparation containers, `start`, `inspect` and `rm` never see the password. The password is read from the private state file and validated as the 48-character hex value `up` generates.

**The application-user SQL path.** `mariadb_app` runs the MariaDB client inside the database container as the OS user `mysql`, as the application account, with `--no-defaults --sandbox --local-infile=0`, no `--force`, `MARIADB_ROOT_PASSWORD` and the other password variables removed from the client's environment, the application password read inside the container and passed as `MYSQL_PWD` (never a host command-line argument), and editor and pager variables neutralised. `guarded_app_sql` runs every Slice 1 check (container identity, server version, sentinel, database allowlist) and then verifies the account itself: exactly one account named `flc_rehearsal`, the client's `CURRENT_USER()` is `flc_rehearsal@%`, and its grants are exactly `USAGE ON *.*` plus `ALL PRIVILEGES ON flc_rehearsal_app.*` (the escaped underscores as `--batch` prints them, doubled backslashes, or the unescaped name), with no role, global, other-database, wildcard or grant-option line. Authentication hashes are cut from each line before comparison; they are never compared or printed. There is no root fallback: if the account lacks something it needs, the operation refuses and names the smallest correction (grant that privilege on `flc_rehearsal_app.*` to `flc_rehearsal`, by hand).

**The probe.** `probe` checks, in order: the account verification above; that the restricted client cannot read the sentinel database; that the client's sandbox does not run `\! <shell command>`; and then, inside the runner, that PHP is 8.3 and uid 33, that an external IP connection and an external DNS lookup both fail, that the root filesystem and the source volume are not writable and `/tmp` is, that the application account connects, sees only `flc_rehearsal_app` and `information_schema`, and is denied the sentinel table. Every runner line must read `ok`.

**Identity and cleanup.** The database container is still identified and protected by the Slice 1 checks and the sentinel. The runner and preparation containers have their own narrow identity check (above), the source volume has its own (plain local volume, labelled `role=source`, this run's token, used by no container but ours), and `self-check` and `cleanup` know about them. `cleanup` selects a labelled container's check by its role label, and keeps (and reports) anything that does not satisfy that complete check; the current PHP image ID is not required for removal. A leftover runner or preparation container stops `run`, `prepare` and `self-check` until `cleanup` has dealt with it.

### L1: the first live validation (passed 2026-11-12)

**Result.** Run once, locally, at commit `872365150ab1`, with the owner's authorization, against synthetic data only. Every stage below passed (steps 1 to 7 and 9; step 8 was deliberately not run, see its note). Verified: MariaDB server 10.11.18 with client 15.1 (10.11.18), which lists `--sandbox`; the application account has exactly `USAGE ON *.*` plus `ALL PRIVILEGES ON flc_rehearsal_app.*`, and `SHOW GRANTS` prints the underscores doubled (`flc\\_rehearsal\\_app`), as the comparison expects; `prepare` archived both trees and installed 79 packages in each from its own lockfile (about 30 s); the source volume was writable by uid 33; all 13 probe lines read `ok`; `run historical about` and `run current about` both reported Laravel 13.32.0 on PHP 8.3.33 (production); `run current helper:db-ping` connected as `flc_rehearsal@%` to `flc_rehearsal_app`. `cleanup` removed the database container, the network and both volumes and the state directory, `self-check` then found no project, and the Docker container, volume, network and image inventories were identical before and after. No migration, restore, import or schema change was run, and the regular development stack and database were not touched. This settles the live-only questions listed under Limits; it does not measure the gateway residual.

The procedure, for a repeat run:

1. Make the historical commit available (`git fetch origin 2f385b79a7b83323c6f15a6685ee610ccd85b5bf`, or `git fetch --unshallow`) and confirm `git rev-parse --verify 2f385b79a7b83323c6f15a6685ee610ccd85b5bf^{commit}`. Check that the development PHP image exists (`docker image inspect flowlife-dev/php:8.3`). If it does not, build only the platform image with `docker compose -f compose.yaml build platform`. Do not run `./flow setup`: it also starts the regular development database and runs migrations, which are outside the rehearsal.
2. `restore-rehearsal.sh self-check` (read-only; expects no project), then `up`.
3. Gate check, read-only: `docker exec flc-rehearsal-restore-mariadb mariadb --help | grep -e --sandbox`. Slice 2.1 was written without access to a MariaDB 10.11.18 client; if `--sandbox` is not listed, stop and report. The script does not weaken the flags.
4. `self-check`: now also verifies the application account through the restricted client. If it refuses, report the grants it saw (`SHOW GRANTS` text, with the hash removed).
5. `prepare`. Confirms the new volume is writable by uid 33 (it relies on Docker copying the ownership of the image's `/var/www/html` into the empty volume) and that both trees install from their own lockfiles.
6. `self-check`, then `probe`.
7. `run historical about`, `run current about`, `run current helper:db-ping`; `run current migrate:status` is optional (a fresh database has no migration table, which is not a failure of the substrate, and L1 did not run it). Do **not** run `migrate`; that is slice 2.2.
8. **Optional, not run in the first L1.** The owner accepted the gateway residual for the synthetic rehearsal without measuring it, so this step was omitted. The network's configuration was only inspected (`internal: true`, gateway `172.25.0.1`). Network boundary, narrow and non-destructive (a measurement, not a scan; no host firewall is read or changed). Read the gateway address with `docker network inspect flc-rehearsal-restore-db --format '{{json .IPAM.Config}}'` (read-only, and not proof of anything by itself). Then, once the runner works (after step 7), with the owner's approval run **one** throw-away container on that network from the same verified PHP image ID, with the runner's isolation options, no credentials and no source volume, that makes TCP *connect-only* attempts (no payload is sent) to that gateway address on two ports the owner names: one where the host is known to listen (for example 22) and one known closed. Report each as connected, refused or timed out. Nothing else on the host, and no address other than that one gateway, is contacted. A connect to a listening host port is a finding to record, not a failure of S2.1. The same container also tries one external IP to confirm the route-out result the probe reports.
9. `cleanup --dry-run`, `cleanup`, `self-check` (expects no project). Record the timings (L1: each stage took between about 1 and 31 s, `up` about 19 s).

## Slice 2.2A: the first half of the recovery cycle

**Status.** Implemented, tested against the fake daemon, and run live as part of L2 (passed 2026-11-14; the first attempt stopped at `take-backup` on a defect in the dump check, since corrected: see L2 below). Any further live run needs the owner's separate authorization. It changes no application code, no migration, no deployment behaviour and no runbook.

**What it proves, and what it leaves.** It builds the production baseline (v0.3.0) in the rehearsal database with the v0.3.0 application, takes the backup the runbook describes, upgrades with the current application, and then reproduces WP3-01 ([audit](../audits/g6/wp3-audit.md), finding WP3-01): loading the historical dump over the upgraded database **without clearing it** leaves the 18 newer tables behind. The corrected restore, which clears the schema first and must make the same inventory check pass, is slice 2.2B and reuses the checks below.

```bash
scripts/rehearsal/restore-rehearsal.sh baseline          # after `up` and `prepare`: v0.3.0 schema, synthetic fixture, snapshot
scripts/rehearsal/restore-rehearsal.sh take-backup       # the runbook's two-pass dump, and its manifest
scripts/rehearsal/restore-rehearsal.sh upgrade           # the current migrations, judged against the snapshot; one synthetic marker
scripts/rehearsal/restore-rehearsal.sh reproduce-wp3-01  # load the dump over the upgraded database; require that the newer tables remain
```

None of them takes an argument. Each starts from the state the one before left and checks it against the database and the state directory themselves, never against a flag, so running them out of order, twice, or against a database that was changed in between is a refusal that changes nothing.

| Stage | Checks before it changes anything | What it does and verifies |
| --- | --- | --- |
| `baseline` | The historical commit `2f385b79…` resolves to exactly that commit; no uncommitted or untracked change under `apps/platform` or `scripts/rehearsal` (`prepare` archives commits, so a dirty tree would be a rehearsal of code nobody is looking at); the target database is **empty**. | Runs the v0.3.0 tree's own `migrate`, so the schema is the one production has and not a replacement. Requires exactly the 16 v0.3.0 tables. Loads `HistoricalFixture` in one transaction (all of it or none) and requires it complete (every table's row count, 13 people). Writes the snapshot. |
| `take-backup` | A snapshot exists; the database still has exactly the 16 tables and still equals the snapshot; no backup exists yet. | The two-pass dump as the application account (never root). Requires the dump to create and drop exactly the 16 tables, carry rows for exactly the 9 durable tables, and name no database. Writes the manifest and re-checks it and the dump's checksum. |
| `upgrade` | A complete, verified backup exists and belongs to this run; the database is exactly the 16 tables and equals the snapshot. | Runs the current tree's `migrate`. Requires exactly the 34 tables and every v0.3.0 table equal to what the upgrade is expected to make of it (the 5 `guardian` role assignments renamed, the 14 migrations recorded, nothing else changed). Writes one post-upgrade Person and CRM profile. |
| `reproduce-wp3-01` | The backup is verified as for `upgrade`; the live keyring holds every key fingerprint the manifest requires; the database is exactly the 34 tables and the post-upgrade state (14 people, 1 marker profile, 29 migrations); the dump's checksum is re-verified immediately before it is loaded. | Loads the dump, then requires the table-inventory equality to **fail** with exactly the 18 newer tables extra and none missing. See below. |

**The historical fixture and snapshot.** The harness (`scripts/rehearsal/php/rehearse.php`) requires the WP3b test support (`HistoricalFixture`, `HistoricalSnapshot`, `UpgradeDatabase::HISTORICAL`) from the prepared current tree by path. The runner installs with `--no-dev`, so Composer's `autoload-dev` is absent; nothing here changes the application's autoloading or installs a test dependency. The fixture is loaded by the v0.3.0 application's own encrypter, so the TOTP ciphertext is what v0.3.0 would have written under the run's key. The snapshot is **digests, never rows**: for each of the 16 tables, its row count and the SHA-256 of its rows as the driver returns them, ordered by primary key (`HistoricalSnapshot::take`), so a changed value, type or order is a different digest, and no hash, ciphertext or secret reaches a log. It also records, from `HistoricalSnapshot::expected`, what the upgrade must make of each table. A query that fails, a table that is absent, a table that appears twice or a line that is malformed is a refusal, never an empty snapshot or a false equality.

**State files.** The snapshot, the dump and the manifest are written into the state directory (mode 600, whole or not at all) as `historical.snapshot`, `historical.dump.sql` and `historical.manifest.json` (slice 2.2B adds `prepared.source` and `upgraded.structure`, below); `cleanup` removes them with the other files the script wrote, by name, and keeps the directory if anything else is in it.

**The backup and its manifest.** The dump follows the [deployment runbook](../runbooks/deployment.md#5-taking-a-backup) exactly: pass 1 is `--no-data --no-tablespaces` (so every table is dropped and recreated), pass 2 is `--no-create-info --single-transaction --quick --no-tablespaces` with the seven transient tables ignored (so they come back empty). It is not compressed; the checksum is of the file that is loaded. The manifest holds the runbook's fields (release, database, dump SHA-256 and byte count, keyring fingerprints, `tables_with_data`, `tables_schema_only`) and a SHA-256 fingerprint of the run token that binds it to the run; it holds no key, password, token, TOTP secret or recovery code. The Resource-files fields are slice 2.2C's. The manifest and the snapshot must agree on the complete 16-table inventory, and its durable and schema-only lists must be the contract's.

**Encryption-key fingerprints.** Each run generates two synthetic keys (`base64:` and 32 random bytes) into the private state file: a current key and a previous one, handed to the runner only through its environment (`APP_KEY`, `APP_PREVIOUS_KEYS`, as variable names, never values). The definition is the runbook's, with its undefined `k` fixed as the **decoded 32 key bytes**:

```
key_fingerprint(k)  = sha256("flc-key-v1|" + k)[0:16]
keyring_fingerprint = sha256("flc-ring-v1|" + join(",", sorted(unique(key_fingerprints))))[0:16]
```

Test vectors (computed independently with Python's `hashlib`; pinned in `scripts/tests/rehearsal.sh`, and the PHP harness reproduces the key ones):

| Key | Fingerprint |
| --- | --- |
| bytes `00 01 … 1f`, `base64:AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8=` | `2c8a734376e488fb` |
| 32 zero bytes, `base64:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=` | `dd55ac8a8f7837a8` |
| 32 bytes of `ff`, `base64://////////////////////////////////////////8=` | `da15800f513e503f` |

| Keyring | Fingerprint |
| --- | --- |
| the first key alone | `aa8b784552ea86fa` |
| the first and second (in either order; a repeated fingerprint changes nothing) | `5fa4bb2695669a8f` |
| all three | `357d42c365bacbce` |

The application reports the fingerprints of the keys it actually used, and the script requires them to be the ones it generated, so the manifest cannot name keys the data was not encrypted with. `reproduce-wp3-01` applies the runbook's subset test before loading anything: every fingerprint the manifest requires must be in the live keyring, or nothing is loaded. (Making this check a gate on every restore is slice 2.2B.)

**How WP3-01 is reproduced and detected.** The dump's pass 1 drops and recreates only the 16 tables it names. Loaded over the 34-table upgraded database it therefore leaves the 18 newer tables. The stage requires four things, each measured, and fails (exit 1, saying what it found) if any is otherwise:

1. `inventory_difference` of the manifest's tables against the database reports **exactly** the 18 newer tables as `extra` and nothing `missing`. This is the same equality a corrected restore must satisfy with an empty difference; here it is required to fail, and only in this way.
2. The post-upgrade CRM profile survives with no Person behind it (profiles without a Person: 1), and the ledger says 15 migrations while 34 tables exist (the next `migrate` would fail: *Table already exists*).
3. Yet the 16 historical tables match the pre-upgrade snapshot (durable tables identical, transient tables empty): a restore that is judged by those tables alone would pass.
4. Everything was loaded through the same guarded application-user path as every other statement, into the one allowlisted database, from the dump whose checksum was verified a moment before.

The demonstration leaves the database in the defective state; slice 2.2B starts from there, or run `cleanup`. If `baseline`, `upgrade` or the demonstration stops part-way, the database may be partly changed: the rehearsal is disposable, so run `cleanup`, then `up`, `prepare` and the stages again.

## Slice 2.2B: the corrected restore, the sign-in and the re-upgrade

**Status.** Implemented, tested against the fake daemon, and run live as part of L2 (passed 2026-11-14). No application code, migration, deployment behaviour or runbook is changed.

```bash
scripts/rehearsal/restore-rehearsal.sh restore-historical   # clear exactly the 34 tables, load the verified dump, verify the result
scripts/rehearsal/restore-rehearsal.sh verify-signin        # the restored v0.3.0 application signs the administrator in (password, TOTP); rolled back
scripts/rehearsal/restore-rehearsal.sh reupgrade            # the current migrations on the restored database, judged against the first upgrade
```

None takes an argument, a file, a database or a statement. `restore-historical` is not a restore tool: it exists to prove the corrected sequence on this rehearsal database, from the one dump this script took.

**Prepared-source identity.** `prepare` now digests the helper scripts **inside the volume** (a sixth container with no network) and refuses unless they equal the ones in the checkout, then records `prepared.source`: the historical commit, the current commit (`HEAD`) and each helper's SHA-256. Every stage (the four of slice 2.2A and the three above) re-derives that text and compares: a missing or non-private record, another historical commit, a `HEAD` that moved, a helper that changed, or any other difference is a refusal that changes nothing. A commit after `prepare`, even a docs-only one, therefore needs `cleanup`, `up` and `prepare` again: the rehearsal says what it ran, and it ran `HEAD` as it was. `run` itself does not check the record (it is the slice 2.1 command).

**Three snapshot states, never mixed.** The snapshot is of the database as the fixture left it. What each later stage compares with is derived from it by one function, and a database is judged against nothing else.

| State | What it is | Where |
| --- | --- | --- |
| ORIGINAL | the 16 tables as loaded, the transient tables with their fixture rows (3 sessions, 2 reset tokens) | the `table` lines of `historical.snapshot` |
| RESTORED | the original with every transient table emptied (zero rows, the digest of none): what the two-pass dump (structure everywhere, rows for the 9 durable tables) restores | `emptied_transients` of ORIGINAL |
| UPGRADED | the original with the 5 `guardian` assignments renamed and the 14 migrations recorded (a 29-entry ledger); after a restore and a re-upgrade, the same with the transient tables emptied | the `upgrade` lines (from `HistoricalSnapshot::expected`), through `emptied_transients` |

Comparison is by one function (`digest_differences`) that reports a name present in only one side as a difference, so a durable table that vanished cannot read as "nothing differs". A snapshot helper that did not print `snapshot:complete=ok`, a table missing or repeated, a malformed line or a structure line missing is a refusal, never an empty or partial result. The row digest is of every value as text (NULL stays NULL), so two application trees whose drivers return `3` or `'3'` do not disagree, while a changed value, a lost row or a different order still does. Structure (columns, indexes, foreign keys of every table, as the engine reports them) is digested the same way: the original's is kept in the snapshot, and the first upgrade's 34 tables in `upgraded.structure`.

**The corrected restore (`restore-historical`).** Every precondition is established **by SQL alone** before any destructive statement, because a database in the WP3-01 state has the newer tables and the older ledger, a state no application can be expected to boot against: nothing starts Laravel against it before the clearing.

| prepared source | as above |

## Slice 2.2C-1: a half-failed upgrade, and a security change made after the backup

**Status.** Implemented, tested against the fake daemon, and run live once (L3a, passed 2026-11-16, [below](#l3a-the-live-half-failed-upgrade-rehearsal-passed-2026-11-16)). The real failure it depends on was measured on MariaDB with the real migration runner by `tests/Upgrade/HalfFailedMigrationTest.php` (below). The slice changes what `restore-historical` is allowed to clear, so it was independently reviewed before L3a was authorized. No application code, migration, deployment behaviour or runbook decision is changed.

```bash

scripts/rehearsal/restore-rehearsal.sh revoke-after-backup   # from the UPGRADED database: remove one role assignment and record its event
scripts/rehearsal/restore-rehearsal.sh restore-historical    # as before, and now also from the half-failed state; says whether it reversed the revocation
```

The order that uses both (the stages in between are the ones above): `baseline`, `take-backup`, `upgrade`, **`revoke-after-backup`**, `restore-historical` (which reports the reversal), `verify-signin`, **`half-fail-upgrade`**, `restore-historical` (from the half-failed state), `verify-signin`, `reupgrade`. `reproduce-wp3-01` is an alternative to `revoke-after-backup` between `upgrade` and `restore-historical`: it loads the dump itself, which reverses the revocation before the restore looks, so nothing is left to report. `half-fail-upgrade` needs the first upgrade's structure record, so `upgrade` must have run in the same rehearsal; it never runs twice without a `cleanup`.

### How the half-failed state is made, and what it is

Production is at v0.3.0 (15 migrations); the next release has 29. A stub table named `person_relationship_field_values` (the **third** table the Relationships migration, the 11th of the 14 pending, creates) is placed in the restored v0.3.0 database, and the real `migrate` is run. Nothing in any migration is changed, and nothing but that one `CREATE TABLE` (a fixed statement, `tests/Fixtures/rehearsal/half-failed-stub.sql`, which the script's own copy is pinned equal to) is placed. The ten migrations before Relationships complete and commit; Relationships creates `person_relationships` and `person_relationship_status_changes`, fails on the third `Schema::create` because the stub exists, and its record is never written. MariaDB commits each DDL statement as it goes and Laravel wraps no MySQL schema change in a transaction, so the first two tables stay.

Measured on MariaDB (the Pest test, real migration runner, real server, the WP3b fixture): the failure is an `Illuminate\Database\QueryException`, SQLSTATE `42S01`, driver error `1050`, on a `create table` of the stub's name; the ledger is the 15 migrations of v0.3.0 (batch 1) and the ten that completed (batch 2), 25 in all, and does not hold the Relationships migration, the rename or the two after it; the schema is 32 tables (the 16 historical, the 13 the ten migrations made, the two Relationships tables and the stub), and `person_relationship_role_provisions` and `sourced_role_grants` do not exist; every historical row is as the fixture left it, the ten migration records apart; and a second `migrate` **does not repair anything**: it fails the same way, on the first Relationships table (which now exists), and changes neither the ledger nor a table. The same test pins that the migration creates the stub's table third, so the failure point cannot move unnoticed, and `t_static_half_failed_lists` fails if the repository's 26th migration is not Relationships.

`half-fail-upgrade` requires, before it places anything, that the database is the verified restored state (`verify_restored_state`: the 16 tables, every durable table equal to the snapshot, the transient ones empty, the original structure, the 15-migration ledger) and that the first upgrade's structure is recorded. It then runs the harness helper `half-migrate` in the **current** tree, which refuses unless the database is exactly the 16 tables and the stub, runs `migrate` twice, and prints, for each run, the exception's class, its SQLSTATE, the driver's code and the table the failed `create table` was creating (never the message), and the ledger and table counts. The script requires `QueryException`, `42S01`, `1050`, the stub the first time and `person_relationships` the second. It then reads the result from the server itself (the 32 tables; the 25 ledger records in order; the stub as the stub) and from the application's snapshot (every historical row as it was, only the ledger differing; the 16 historical tables' structure the original's; the structure of 14 of the 15 committed tables the first upgrade's; `contact_methods` what its creating migration left, below; the stub not the real table). Only then does it write `halfmigrated.state`: a digest of the schema as the server reports it and a digest of selected columns of `role_assignments`, `accounts` and `security_events` (listed under "Which checks, and when"). A refused stage writes nothing.

**`contact_methods` is not the first upgrade's table, and the rehearsal says so.** The first upgrade ran all 14 migrations. The 29th, `2026_10_11_000001_add_provenance_to_contact_methods`, adds the nullable `updated_by_account_id` to `contact_methods`; the half-failed state stops at the 26th (Relationships), so its `contact_methods` is exactly what `2026_10_01_000002_create_contact_methods_table` made, without that column. Comparing all 15 committed tables with the first upgrade's structure therefore refused the real half-failed state on `contact_methods` and on nothing else (found by the independent review before any live run). Now the 14 others are still compared digest for digest, and `contact_methods` is held to a written-out structure instead: `tests/Support/HalfFailedShape.php` lists its nine columns, four indexes and one foreign key as the creating migration made them, and the helper prints `half-migrate:contact-methods-structure=ok`, or the names of what differs, from that same code. The script requires `ok`, and also requires that the table's digest is **not** the first upgrade's (the provenance migration has not run). `HalfFailedMigrationTest` measures this on a real MariaDB: the fully upgraded table has the column; the half-failed one does not; the old all-15 comparison refuses exactly `contact_methods` and the other 14 are identical; the half-failed table equals the written-out structure; the fully upgraded table minus that one column equals it; the fully upgraded table is rejected as `unexpected column updated_by_account_id`; and an extra column, a missing one, another type, a nullability change, a missing or non-unique index, and a changed or missing foreign key are each rejected, in the comparison and on a real altered table. The comparison is by name and leaves out the collation, charset and comment (they follow the rehearsal database, not the migration); the schema digest `restore-historical` checks covers the whole table as the server reports it. The fake daemon's `contact_methods` digest is no longer the same as the first upgrade's, so the happy-path test would fail under the old comparison (shown once against a scratch copy of the script).

It accepts three starting states and no other, each with the table set and counts that go with it and no other pairing:

| State | Tables | Counts (Persons, CRM profiles, migrations, profiles without a Person) |
| --- | --- | --- |
| Upgraded (`upgrade`) | the 34 | 14, 1, 29, 0 |
| After `reproduce-wp3-01` | the 34 | 13, 1, 15, 1 |
| **Half-failed (`half-fail-upgrade`)** | **the 32** | **13, 0, 25, 0** |

For the third, every one of these is established by SQL alone (no application is started against the partial schema), and any one failing refuses before anything is cleared: the verified backup, manifest and keyring and the source identity (as for the others); plain base tables only, and no view, trigger, routine or event; the exact 32 table names, from the script's own lists; the 25 migrations by name, in order, with their batches; the stub read back from the server (a base table, InnoDB, `utf8mb4_unicode_ci`, the marker comment, one column `stub CHAR(1) NOT NULL`, no index, no foreign key, no row); every one of the 16 newer tables empty; the eight durable tables' row counts the fixture's; the state file present, private and exactly the shape the stage writes; and the schema and the security tables digesting to what that stage recorded. **It does not become a generic partial-schema recovery tool:** a different table set, a table that is missing or extra, a view, a reordered, missing or additional migration record, a different stub, a changed column or index or key or rule, a changed row in `role_assignments` or in the columns of `accounts` and `security_events` the security digest covers, a half-failed state this script did not make (no state file), or the counts of another state all refuse, and `restore-historical` still takes no argument, file, name or SQL. It does **not** claim that any changed row is refused: see the next section.

### Which checks, and when

Three different verifications of the historical data, which are not the same strength:

1. **When the half-failed state is made (`half-fail-upgrade`).** Every historical row, of every one of the 16 tables, is compared with the pre-upgrade snapshot through the application (only the migration ledger may differ), and so is every table's structure. This is the full check.
2. **Repeated before anything is cleared (`restore-historical`).** SQL alone, no application. The schema digest (tables, columns, indexes, keys, as the server reports them), the 25 migration records, the stub, empty newer tables, the **row counts** of the eight durable tables, and a digest (MD5 of the concatenated text) of these columns only: `role_assignments`: `id`, `person_id`, `role_key`, `granted_by_account_id`, `granted_at`; `accounts`: `id`, `person_id`, `email_canonical`, `status`, `security_generation`, `disabled_at`; `security_events`: `id`, `occurred_at`, `type`, `actor_account_id`, `subject_person_id`, `outcome`, `context`. A change to another column, or to another durable table (`people`, `account_invitations`, `account_recovery_codes`, `account_totp_factors`, `membership_grants`), that leaves the row counts unchanged is **not** detected at this point: for example `people.display_name`, `accounts.password_hash` or `account_totp_factors.secret_ciphertext`. The digest is also an MD5 of `GROUP_CONCAT` output, which is silently cut at `group_concat_max_len` (1 MiB by default, fine for this fixture, not for a large database), and it does not distinguish NULL from an empty string. Both limits are accepted for this small synthetic fixture.
3. **After the restore.** `verify_restored_state` compares every row of every durable table and every table's structure with the snapshot, and refuses on any difference. A same-count change made after step 1 is therefore never kept: the cleared tables are replaced by the verified dump and the result is checked in full. What step 2 leaves open is only whether this was the database `half-fail-upgrade` made, which for a disposable, isolated, synthetic rehearsal is accepted.

The statement that clears is built from the script's own lists for the state it recognised: the 34 names, or the 32 (the 16 historical, the 15 committed newer tables and the stub; neither table the failed migration never reached). It is one `DROP TABLE` with no `IF EXISTS`, no `DROP DATABASE`, no wildcard and foreign-key checks off for that one session. After it the inventory must be empty, the dump is re-verified, loaded, and the result judged exactly as for the other states: the 16 tables, every durable table and the structure equal to the original snapshot, transient tables empty, the 15-migration ledger. `reupgrade` then compares the result with `upgraded.structure`, the first upgrade's record, which this slice leaves as it was.

### The security change, and its reversal

`revoke-after-backup` runs from the upgraded database. In one transaction it does what the application's `RevokeRole` does: it removes Person 3's role assignment (the `guardian` the upgrade renamed to `guardian-full`) and records a `role.revoked` event. The backup, taken before the upgrade, holds neither. The script reads five numbers (role assignments, security events, that assignment present by exact bytes, `role.revoked` events, and the one event with the fixed id `HistoricalFixture::id('E', 9)`, type `role.revoked` **and subject Person 3**) before it (12, 8, 1, 0, 0) and after it (11, 9, 0, 1, 1), and refuses anything else. The fifth number is what ties the event to Person 3: the fourth alone counts any `role.revoked` event, so an event for another Person would give the same four numbers. A test plants exactly that (11, 9, 0, 1, 0) and the stage refuses.

`restore-historical`, from an upgraded or WP3-01 database, reads the same five numbers before it clears. Only if they are the revoked ones (11, 9, 0, 1, 1) does it expect a reversal, and after the load, once the restored database has passed every other check, it reads them again and **refuses unless they are 12, 8, 1, 0, 0**: the assignment is back and the event is gone. An event of another Person with the same four overall counts is not this stage's revocation, so no reversal is claimed for it. The resurrection of the assignment and the erasure of the event are established independently by `verify_restored_state`, which has already compared every row of `role_assignments` and `security_events` with the backup's snapshot. It then says so, in plain words: an apparently successful restore resurrects authority that was revoked after the backup and erases the record that it was revoked; if this were production, the service stays in maintenance, the security state is not established, and the operator escalates. It does not reconcile, replay or repair anything, no such command exists, and none is added. It makes no claim for any other security state: where the five numbers are not the revoked ones, it says nothing.

### What this does not show

It was run live once (L3a, below), on synthetic data and one local machine. It rehearses one half-failed migration (one stub, one failure point) and one authority-reducing change, on synthetic data. It does not rehearse Resource files, preserving the failed state, security reconciliation, or the host. A real half-failed migration may stop elsewhere or leave a different partial schema; the rehearsal clears only the one it made, and a production half-failed state is **not** to be cleared by anything here. The runbook's decision table for a stopped `migrate` is still unwritten.

### The files volume and the files container

The rehearsal owns one more volume, `flc-rehearsal-restore-files-data` (role `files-data`), and runs one more disposable container, `flc-rehearsal-restore-files` (role `files`). The volume is created, labelled with the run token, only by the **first files action of `seed-files` or `backup-files`** (so the zero-file backup, which may be the first files action, still establishes it), and removed by `cleanup`. Once it has been verified the script records that in a private state file (`files.volume`, bound to the run token); **a volume that is missing after that is refused and never recreated** (a new, empty volume must not silently take the place of one whose files are gone), and `aside-files`, `restore-files` and every later action of a command refuse a missing volume instead of creating it. **Its root is the application's `storage/app/private`**, so the directory the files commands call `resources` is exactly the private `resources` disk's root (`config/filesystems.php`: `storage_path('app/private/resources')`). A test holds that: `ResourceFileArchiveTest` runs the application's real `DiskResourceFileStore` over this layout and lists and opens every seeded file, and `t_static_the_files_slice_is_what_the_contract_says` holds the script's constants to the disk's configuration.

The container is a different thing from the PHP runner:

| | PHP runner | files container |
| --- | --- | --- |
| Network | the internal database network | **none** (`--network none`) |
| Credentials | the application database password and the synthetic encryption keys | **none**: no environment variable at all, created by the launcher that carries no secret |
| Application | the application tree, booted | **none**: plain PHP and `tar`, reading only the helper and two support classes |
| Mounts | the source volume, read-only | the source volume (read-only) at `/rehearsal/src`, and the files volume at `/var/www/html`, **read-only unless the action writes** |
| Root filesystem, user, capabilities, limits, no-new-privileges, no published port | as G10 | the same (it goes through the same verification) |
| Docker socket, bind mounts, host paths | none | none |

Which actions may write is a table in `files_action_policy`: `check`, `archive` and `verify-archive` get the files volume read-only; `seed`, `aside` and `restore` get it writable; any other name is refused. The container is verified against what was asked of Docker **before it starts**, and its mounts are compared as a sorted set, because the daemon does not promise an order and this container has two. `/var/www/html` is also an existing, `www-data`-owned directory of the image, which is why a new volume mounted there is writable by uid 33 (the same mechanism the source volume relies on, proven live for that volume in L1; **not yet proven for this one**). The helper additionally refuses unless `/var/www/html` is a mount point of its own container, so a container started without its volume cannot report an "absent" directory that is really the image's.

The files volume has its own identity check (`files_volume_identity_problem`, guards `G22-v-*`): name, plain local driver with no options (no host path), labels, run token, and no container but ours using it. Cleanup dispatches on the volume's name, so the files volume is removed only if that check holds, and the files container only if its complete identity holds; both are re-verified just before removal, as the other objects are. `self-check` verifies the files volume when it exists. `foreign_lookalikes` names an unlabelled object with either new name and `up`/`self-check` refuse beside it.

### What the files commands do

`seed-files` starts only from the exact post-upgrade state (the 34 tables, 14 Persons, one CRM profile, 29 migrations, no profile without a Person) with an existing, empty `resource_assets` table. The container writes four files (64, 1,500, 9,000 and 33,333 bytes of deterministic content, keys `01jcf000000000000000000001` to `…004`, mode 0600, modification time 2026-01-01) into a Resources directory that must not exist; the script then inserts one `resource_assets` row for each in one transaction, reads the rows back, and holds the directory to them. It simulates uploads made after the upgrade; the rows reference no Card.

`backup-files` runs from the 16-table or the 34-table database (anything else is refused) and never overwrites a backup. It reads the asset rows with two fixed statements (is there a `resource_assets` table; its `storage_key`, `byte_size`, `sha256`), runs `check`, and requires the directory and the rows to agree **on every key, byte size and SHA-256**. An absent directory is a zero-file backup only when the table does not exist or has no rows. Then:

- **absent directory:** no archive container is run, no archive is made; the manifest records `resource_files_count: 0`, `resource_files_sha256: null`, `resource_assets_rows` `null` (no table) or `0`;
- **existing directory** (empty or not): `archive` runs the runbook's command, `tar -C <private> -czf <archive> resources`, with its exit status checked, reads the archive back with a strict reader of its own, and holds it to the directory's inventory; the script receives the bytes on standard output into a private temporary file, has a second container verify that file against the listed files, and only then moves it into the state directory and writes the manifest. An empty directory is archived, as the runbook's step 2a says, with a count of 0 and a checksum of the archive.

`aside-files` is the runbook's step 2: one rename, inside the volume, of `resources` to `resources.before-restore-<YYYYMMDDTHHMMSSZ>` (a name the script builds from its own clock; no path comes from a caller). It **requires a verified Resource-files backup first** (the same manifest and archive checks `restore-files` makes, before the files helper runs), and it **measures the preservation**: the helper reads the directory with the same inventory rules `backup-files` uses immediately before the rename and the renamed directory immediately after, prints both (`before:` and `after:` lines of key, size and SHA-256, never content), and refuses on any difference or unreadable entry; the script validates each inventory itself, requires them to be identical, and then confirms the original place is empty. A directory the inventory refuses (a link, a subdirectory, a stray file) is refused *before* the rename. A failure after the rename leaves the moved directory where it is: nothing is renamed back or removed. It refuses if there is no directory or the name is taken, and never deletes, merges or overwrites. `restore-files` verifies the stored archive against the manifest **first** (a read-only container, no write), then extracts it into a volume with no Resources directory, then holds the result to the manifest twice (the extracting container's own read-back, and a second, read-only container). A zero-file backup extracts nothing and requires the directory to be absent; it does not remove one. It does **not** restore the database, run `resources:assets:prune`, or reopen anything.

### The archive and the manifest

The archive is `resources.archive.tar.gz` in the private state directory: what the runbook's command writes, with `resources/` first and `resources/<storage key>` regular files, and nothing else. The reader (`ResourceFileArchive::readArchive`) accepts only that: one complete gzip stream with nothing after it and an expanded size under 16 MiB; whole 512-byte tar blocks ending in two zero blocks and nothing else; each header's checksum valid, `ustar` format, no name prefix, no link target, no setuid, setgid or sticky bit; entry types limited to the directory and regular files; names exactly `resources/` and `resources/<26-character lowercase ULID>`; no duplicate; zero padding. A symbolic link, hard link, device, FIFO, pax or GNU long-name header, a subdirectory, `../`, an absolute path, `./resources/…`, a nested or doubled path or another top directory is refused for what it is.

`resources.manifest.json` carries the runbook's Resource fields, `resource_files_sha256`, `resource_files_count` and `resource_assets_rows` (`null` where there is no table), plus the archive's name and byte count, a UTC time, the SHA-256 fingerprint of the run token (binding it to this run) and one line per file with its key, byte size and SHA-256. It holds no key, password, token or content. It is never accepted for recording a state: an absent directory records no archive, checksum or files; a present one records the archive's fixed name, a SHA-256, a positive size and a count equal to the files listed; `resource_assets_rows`, where there is a table, equals that count; and the whole file must equal what the script itself would write from the values it read (so an extra, missing or reordered line is refused). The archive's byte count and SHA-256 are checked against it before anything is extracted. The `archive:entries=` count the verification reports is the number of entries the reader accepted, counted from the archive itself.

### What is refused

Each is a refusal that ends the command, with nothing repaired, moved or written past it. In the PHP logic (tested on a real directory with the real `tar`): an absent directory while rows exist; files with no table; a missing file; an unexpected file (however young); a file not named as a storage key; a subdirectory, a symbolic link, a hard link or another non-regular entry; changed content under an unchanged name (and a changed size); a Resources path that is a symbolic link or a file; a failed or empty `tar`; an archive with an incomplete or oversized gzip stream, trailing data, a bad header, an unexpected, missing or duplicated entry, a traversal or absolute path, a size or checksum that is not the recorded one; extraction over an existing `resources`; extraction that changes anything; a stamp that is not a UTC time; an aside whose name is taken. In the script: every unexpected output of the files container, and the manifest and archive conditions above.

### Slice 2.2C-3, WU2: the runner reads the Resources volume for one operation; every runner is rechecked after its create (implemented; fake-daemon tested only, not run live)

- **What may see the files volume.** Exactly one runner: `run current resources:assets:prune`, whose vector is `php artisan resources:assets:prune --dry-run` (`PRUNE_DRY_RUN_CMD`, from which `runner_command` builds it). `run_in_runner` asks `runner_may_read_files WORKDIR CMD...`, which compares the vector it is about to run, element by element, with that constant, and the tree with `current`. - **`run historical resources:assets:prune` is refused.** The historical tree is not given the files volume, so the dry-run there would report an empty store whatever the volume holds (or fail for want of the command in that tree), which reads as a finding and is not one. `run_in_runner` refuses it, before any rehearsal object is inspected or created (the general preflight, including the daemon check, has run), and says to run the current tree's. - **Checks before the create.** The prune runner needs the files volume to be an *established* one: the record in the state directory must exist (a volume of that name with no record is not adopted), and `files_volume_ready TOKEN 0` (no permission to create) proves the record is this run's, the volume exists (a missing established volume is refused, never replaced, never read as an empty store), is plain local with the rehearsal's labels and this run's token, and has no consumer. This operation never creates the files volume.
- **The mount, and why it is where it is.** The files volume's root is the application's `storage/app/private` itself (the files helper mounts it at `/var/www/html`), so the Resources disk's root, `storage/app/private/resources`, is `<volume>/resources` (`ResourceFileArchive::STORE`, the script's `FILES_STORE_DIR`) and a file is `<volume>/resources/<storage key>`. The runner's `storage` is a tmpfs, and the volume cannot simply be mounted over the Resources directory: it holds the directory, not its content. The volume is therefore mounted **read-only at `/rehearsal/files`**, a path of its own (not under the application: Docker copies an image directory's content into an empty named volume mounted over it, and the source volume is read-only at `/var/www/html`), and `RUNNER_FILES_SETUP` makes `storage/app/private/resources` in the runner's tmpfs a link to `/rehearsal/files/resources` (the directory name is written into the setup text from `FILES_STORE_DIR`) before running the command. The link lives only in the container's tmpfs. Both ends are proven in the container before the command runs: the directory in the volume must be a plain directory whose physical path is exactly that one (a link elsewhere, a dangling link or a file is refused), and the link must resolve to it; a directory of that name already in the tmpfs is refused too. Any of these is exit status 70 with nothing run. A volume with **no** Resources directory (the zero-file state) gets no link, and neither does one holding only a set-aside `resources.before-restore-<stamp>`: the application finds the empty store it finds on a new installation. Nothing is written to the volume. The command's own output and status are the container's. The mapping text is run for real, against directories laid out as the files helper lays them out, in `t_g24_the_files_mapping_is_made_inside_the_runner`; `t_g24_the_runner_mapping_agrees_with_the_files_helper_layout` holds `FILES_STORE_DIR`, the files volume's mount and the setup text to `ResourceFileArchive::STORE`, the files helper's root and the application's disk configuration, so the helper and the runner cannot disagree about where the files are. It needs only POSIX `sh`, `ln`, `mkdir` and `cd`. A read-only Flysystem root that is a link was also checked once with the application's pinned `league/flysystem-local` outside Docker (the link is followed for the root and `links => skip` applies only to what is in it; a dangling root throws, an absent one is created lazily, which is why the absent case makes no link).
- **After the create, for every runner.** `runner_mounts_recheck` proves the source volume again (and, for the prune runner, the files volume), with the new container as the only consumer allowed, before `start_and_remove`. A missing volume that Docker made (empty, unlabelled), a replaced volume, a relabelled one or one a foreign container began to use is refused: nothing starts, only the container this script just created is removed (and only if `ephemeral_identity_problem` still proves it is the one it created; otherwise it is left and the refusal says so), and no volume is touched. `files_mounts_recheck` and this one share `refuse_after_create`, whose message no longer says that no volume was changed: it says this script removed none and that Docker may have made one again. The identity check of the created runner (`ephemeral_identity_problem`) also requires the prune runner's mounts to be exactly the two read-only volumes at the two paths.
- **Implicit volume creation is a recorded change.** `mutation_begins` is called in `run_in_runner` just before the create, so any armed stage that gets as far as asking Docker for a runner says "may be partly changed" afterwards, for the read-only helpers too (the F3 list of read-only helpers now only says which commands need no record *of their own*); refusals before it keep the "stopped before it began to change anything" trailer.

### Slice 2.2C-3, WU4: the current-schema profile, `snapshot-all`, `backup-paired` and the recovery manifest (implemented; fake-daemon and real-PHP tested, not run live)

WU4 adds the first half of the paired recovery: one backup of the **current** schema that holds the database and the Resource files together. It does not restore anything. The historical profile (the 16 tables of v0.3.0, nine durable, and `baseline`, `take-backup`, `restore-historical` and the rest of the first cycle) is unchanged: no historical stage's function was edited and no historical stage calls anything added here. (Five existing lines gained an entry for the new names: the lists `SUPPORT_FILES` and `STATE_FILES`, the approved-helper and read-only-helper lists, and the usage text.)

- **Two profiles, chosen by the stage, never by the caller.** *Historical*: 16 tables, 9 durable (`migrations` among them), 7 transient. *Current*: 34 tables (the 16 and the 18 newer ones), 27 durable, the same 7 transient (`cache`, `cache_locks`, `failed_jobs`, `job_batches`, `jobs`, `password_reset_tokens`, `sessions`), 29 migrations (`CURRENT_LEDGER_COUNT`, ending at `CURRENT_LAST_MIGRATION`, both held to the repository's migration files by a test). A function belongs to a profile by its name (`current_dump_problem` beside `dump_problem`, `current_durable_inventory` beside `durable_inventory`) and no command takes a profile, a table, a file, a database or a statement. The current files have names of their own (`current.dump.sql`, `recovery.manifest.json`), and `cleanup` removes them.
- **`snapshot-all` (a read-only helper, `rehearse.php snapshot-all`, run as `run current helper:snapshot-all`).** It reads all 34 tables with the application's own connection and prints, never a value: the fingerprints of the keys the application used; `all-table <table> <rows> <digest>` for each table (a kind of its own, so nothing reads it as the 16 `table` lines of `snapshot`, which is unchanged); the structure digest of each table (the code `snapshot` already used); and the ledger's count, last migration and digest. The row digest is `Tests\Support\CurrentSnapshot::digest` over the rows **in the order of the table's primary key as the engine reports it** (every table has one; a table without one is a refusal, and so is one that is a view, one that is missing, one that is not among the 34, and an empty or malformed ledger), each value as text with NULL kept, and it is the digest `rehearse.php` already made for the 16 (a test holds the two equal). It does not depend on the order rows were written, and a change and its exact reversal gives the same digest, which is why the backup's claim below is "no change was observed". The script validates the output as completely as the historical snapshot's: exactly one line for each of the 34 tables, well formed, a ledger of 29 ending at the expected migration, the keys the run generated, and `snapshot-all:complete=ok`; anything else is a refusal, never a smaller snapshot.
- **`backup-paired` (a fixed stage, no argument).** It starts only from the upgraded database (exactly the 34 tables and the post-upgrade state: 14 Persons, one marker profile, 29 migrations) with the four seeded Resource files and their four asset rows, and an established files volume. Then, in this order:
  1. *Measure.* The two reads of the asset rows (SQL), the Resources directory held to them by the files container (every key, size and SHA-256), and `snapshot-all`. The application's snapshot and the SQL read must count the same `resource_assets` rows.
  2. *Dump.* The documented two-pass dump (structure of every table, rows of the durable tables only) as the application account, checked line by line against what the first measurement counted (below).
  3. *Archive.* The files container's `archive` and `verify-archive`, the same actions `backup-files` uses.
  4. *Measure again.* Any difference from the first measurement, in any table's rows or structure, the ledger, any Resource file or any asset row, refuses the stage.
  5. *Verify the unit, then put it in place.* The Resource-files manifest (the L3b format, unchanged) and the recovery manifest are written to temporary files, the whole unit is verified from those files, and only then are the four files put in place, by a hard link that fails if the name is taken: the dump, the archive, the Resource-files manifest and **last** the recovery manifest. The unit is verified again from the files as put in place.
- **What "one recovery unit" claims, and what it does not.** A dump and an archive are two commands. Both succeeding proves nothing about when each saw the data, and the dump's two passes are two as well (pass 2 alone is one transaction, `--single-transaction`). The claim is **"no change was observed"**, from: (1) the rehearsal database is private, reached only through this script's own containers one at a time under the one-run lock, and no other rehearsal container exists (every container the script creates checks that), so nothing else writes between the steps; (2) the measurements before and after both artifacts; (3) the dump holding exactly the first measurement's row count for every durable table and nothing for the transient ones; (4) the archive read back against the files measured. It is detection by before/after equality, **not isolation**: a change made and exactly reversed between the two measurements is not noticed, and the script says "not an atomic snapshot" in its output. Making it atomic would need a lock the application account does not have (and must not get), or stopping the application, which has no meaning in a private rehearsal.
- **Partial failure.** Nothing is put in place until the unit has been verified, and a temporary file is removed when the stage ends, whatever the reason. If putting the files in place stops part-way (a file appeared under one of the names after the stage began), what had already been put in place stays, is named, and is said **not** to be a recovery unit, because the recovery manifest is the commit point and was not written. The next `backup-paired` refuses (it never overwrites) and the rehearsal is cleaned up and started again; nothing is repaired, renamed back or removed by the script. `require_recovery_unit` refuses such a state: without `recovery.manifest.json` the other files are not a unit, whatever they hold, and the historical backup's files (`historical.*`) are never one.
- **Dump verification for the current profile (`current_dump_problem FILE TABLE_LINES`).** The historical `dump_problem` reads a dump for table names and requires an `INSERT` for every durable table, which is false for a migrated database (`mariadb-dump` writes no `INSERT` for a table with no rows). The current check is stricter in one way and different in another. Every line of the dump must be one of these forms, and a statement of any other kind is refused, never skipped: comments and blank lines; `/*M!999999\- enable the sandbox mode */`; a conditional `/*!NNNNN SET … */;` (or `/*M!NNNNNN SET … */;`); `/*!40000 ALTER TABLE `t` DISABLE|ENABLE KEYS */;`; `DROP TABLE IF EXISTS `t`;`; a `CREATE TABLE `t` (` whose body is the lines indented two spaces, up to `) ENGINE=…;`; `LOCK TABLES `t` WRITE;` and `UNLOCK TABLES;`; and `INSERT INTO `t` VALUES` followed by one line for each row, `(…),` and the last `(…);` (the form observed live in L2; the single-line form is not accepted). Then: exactly the 34 tables created and dropped, once each; no `INSERT` for a transient table; for each durable table **as many row lines as the first measurement counted rows** (so an empty durable table has none, and is not "missing", and a durable table that held rows but has none in the dump is refused); and nothing for a table outside the 34. A `/*!… */` comment is accepted only as a `SET`, so `/*!40101 SET x */; DROP DATABASE y;` and `USE`, `CREATE DATABASE`, `DELETE`, `TRUNCATE`, `GRANT`, `INSERT IGNORE`, `REPLACE` and a column-list `INSERT` are all refused.
- **The recovery manifest (`recovery.manifest.json`, `recovery_manifest_version` 1).** One fact to a line. It reuses what L2 and L3b proved by **reference**: the Resource-files manifest is `resources.manifest.json` as it is, bound by its SHA-256 and size, and the database part uses the historical manifest's field names. It records: the backup id and time; the run token's fingerprint (never the token); the release (`version` `unreleased`, because the tree under test is a commit, not a tag, and `release.json` is made by `./flow release build` and is not in a `git archive`; and the commit the source volume was prepared from); the server version; the keyring fingerprints (never a key); the dump (file, SHA-256, bytes); the ledger (count, last migration, a digest of every name in order); an aggregate digest of the structure; the durable (27) and schema-only (7) lists; the Resource-files manifest (file, SHA-256, bytes) and the archive (file, SHA-256, bytes); the file count, the asset-row count and a digest of the file inventory; and one line for each of the 34 tables: name, class, rows, the digest of its rows and of its structure. No secret of any kind.
- **What the verifier (`recovery_unit_problem`, wrapped by `require_recovery_unit`, which WU5's restore will call) refuses.** It takes the four files and reads nothing from the database. A manifest is never accepted because it says what it should: every fact is recomputed from the files, and the whole document must be exactly what `recovery_manifest_text` writes from what it says, so a changed value, an extra, missing, repeated or reordered line is found. It refuses: a missing or non-private file (or a symbolic link); another version; another run (the token's fingerprint) or the manifest of another run; a release commit that is not the one the source volume was prepared from (the historical commit included); another database or server version; a keyring that does not follow from the fingerprints listed, or that needs a key this run does not hold; a dump whose name, SHA-256 or size is not the manifest's, whose statements are not the forms above, or whose rows are not those the manifest says the database held (a corrected checksum does not hide that); a ledger that is not the 29 migrations; a table list that is not exactly the 34, in order, with classes that are not the contract's; durable and schema-only lists that are not the 27 and 7; a structure digest that is not that of the digests listed; a Resource-files manifest that is not consistent on its own (the L3b rules), not the one bound, or not taken at the same time; a unit whose Resource files are not a directory holding files (a zero-file manifest is valid on its own and is not a paired backup of a database with Resource-file records); an archive that is not the one the manifest describes; and a file count, asset-row count, measured `resource_assets` rows and inventory digest that are not one number.
- **Guards and the evidence for them.** 54 new `# guard:G25-…` markers, each held by a test that removes it in a copy of the script and requires a test to fail for that guard's reason. The PHP side has its own eight (`// guard:S-…` in `CurrentSnapshot`), mutated by `CurrentSnapshotTest`. Tests: `t_g25_*` (the stage, the measurement, the second measurement, the dump as a validator and as part of the stage, failures and the evidence they leave, double invocation, the manifest, the artifacts, substitutions, the separation of the profiles) and `t_static_wu4_lists_agree`; Pest `Unit/Rehearsal/CurrentSnapshotTest.php` (the 34 tables and the 27/7 classification, the digest, the ledger evidence, the protocol lines, the eight guards) and `Feature/Rehearsal/CurrentSnapshotDatabaseTest.php` (the real migrated schema is exactly the 34 tables, each with one primary key; the 29 migrations; the same snapshot every time; the digest of a durable table, of tables of other shapes and of a transient table changes when a row is added, changed or removed and no other digest does; the order rows were written in does not matter).
- **Source identity.** `CurrentSnapshot` and `CurrentSnapshotRefusal` are the two support classes `snapshot-all` loads by path, so `prepare` attests nine, not seven (`SUPPORT_FILES`); **a source prepared before WU4 must be prepared again.** `prepared-v2` is otherwise unchanged.
- **Not claimed: what needs a real Docker measurement.** Everything above ran on the fake daemon and, for the PHP, on the real migrated schema; nothing ran against Docker in WU4. In particular: (1) **the dump's exact line forms**. The accepted forms were composed from the tool's documented output and from the one form observed live (L2: rows on the lines after `VALUES`); no 34-table dump of a real MariaDB 10.11.18 was read. A form that list lacks (a conditional comment of another shape, a `CREATE TABLE` whose last line differs, a row `mariadb-dump` splits over several lines, a long table split into several `INSERT`s that this check would count correctly but has not seen) would refuse a good dump, which is the safe way to be wrong, and it would be found by the first live probe; (2) that `snapshot-all` runs in the runner within its limits on the real 34-table schema (its logic ran on a real database in the Feature test, outside the runner); (3) that the real server's version string, the real keys' fingerprints and the real archive agree with what the manifest checks (each is what an earlier live run already used); (4) the time the extra two runners and two files containers add. A real 34-table dump probe is the first thing L3c (or a smaller separately authorised probe) should do.
- **What WU3 and WU5 may rely on.** `require_recovery_unit` is the one question a paired restore asks before it touches anything: it needs no database and returns a refusal naming the first fact that is wrong. The unit's files are `current.dump.sql`, `resources.archive.tar.gz`, `resources.manifest.json` and `recovery.manifest.json`; `files_backup_required`, `aside-files` and `restore-files` read the last three as they always did, and `backup-paired` and `backup-files` are exclusive in one run (each refuses if the other's files exist). The manifest's table lines give a restore, for every one of the 34 tables, the rows and digests to compare the restored database with (transient tables are measured with their rows, and a restore leaves them empty, as `restore_state_differences` already says), the structure digests (equal to those `upgrade` recorded in `upgraded.structure` for the same schema), the ledger, the durable and transient lists and the keyring. `snapshot-all` is the measurement to take after a restore and compare with them. `current_dump_problem` judges any dump against a set of table lines, so a restore can re-verify the dump it is about to load. WU3's `preserve-failed-state` and `aside.record` and WU5's `drift`, `change-after-backup`, `restore-paired` and final verification are not here.

## The safeguards

Each is one line in `restore-rehearsal.sh` carrying a `# guard:<ID>` marker.

| --- | --- |
| G1 | The daemon is the local one: `default` context, a unix-socket endpoint, reachable. Every `docker` call runs under a scrubbed environment, so `DOCKER_HOST` is refused even when it names a unix socket (it would not be the daemon acted on). |
| G2 | No inherited database, application or Compose override. Checked before any Docker call. |
| G3 | Credentials and the run token are generated per run into a private file and never printed. No `.env` is read, and one beside the compose file is refused. |
| G4 | Identity is verified against the object itself (name, image, labels, network, mounts, ports, privilege, run token), not trusted from a label. | G5 | The sentinel database holds the run token. Every SQL statement is preceded by checking it matches this run's token. |

## Tests

`scripts/tests/rehearsal.sh` (run by `./flow check repo`) creates no container, network, volume or database. It runs the script against a fake `docker` in a private tool directory that contains no real `docker`, so a mistaken test cannot reach the daemon. It also renders the committed `compose.yaml` with `docker compose config`, which starts nothing.

**Two modes** (CI-1; [testing](testing.md#verification-tiers)). With no argument the file runs the **full** verification: the ordinary tests, the registry check and the whole mutation matrix below. `--routine` runs the **routine** verification, which is what `./flow check` and CI run: every ordinary test once and the registry check in both directions, and no mutation experiment (it says `Mutation matrix: NOT RUN`). The mode is an argument and nothing else; anything malformed is refused before a test runs. The routine run shares the ordinary tests among worker processes (CI-2: `REHEARSAL_WORKERS` unset means up to four, `0` means this process, one after another; see [testing](testing.md#the-recovery-rehearsals-guard-tests)), and judges each worker's records so that a test counts as run only when it was reported exactly once by the worker it was assigned to; the full run's workers still share the mutants, and the matrix's accounting is unchanged. **Any change to `restore-rehearsal.sh`, its PHP helpers or `scripts/tests/rehearsal.sh` still needs the complete local mutation matrix (`./flow check --mutation`) before an independent review handback**: a routine run cannot show that the tests still catch the removal of each guard, and a change elsewhere in the script can make an unchanged guard's test stop catching it (WU2's `G23-helper-mutation`).

The full run then runs a mutation matrix: for each guard it replaces the marked line with `:` in a scratch copy and requires a test to fail. A marker without tests, or tests without a marker, fail the run. Markers sit on the safeguards' bodies and also on the call sites whose removal would be a safety loss: the environment refusal in `up`, the state-directory checks in `cleanup`, the container, network, volume and version checks `up` makes before it writes to the server, and the identity and version checks every SQL statement is preceded by. Properties a line replacement cannot express are pinned by tests of their own: that the state directory is only ever emptied of the files the script wrote and removed with `rmdir`, never recursively (including an entry that appears while it is being emptied), and that a dry run against a complete project leaves every Docker object, every state file, its content and its permissions as they were (only the lock file is touched: the script opens it to take the lock).

Slice 2.2A adds tests for each stage and guard. The fake stands in for the PHP harness too: for each helper a test says what it prints, what it changes in the world afterwards, or that it fails. The three state files the later stages need are made once by the real script's earlier stages and copied. Lists the script holds (the 16 historical tables, the 18 newer ones, the 7 transient ones, the fixture's row counts) are pinned against `HistoricalSnapshot::TABLES`, `HistoricalFixture::NEW_TABLES`, the deployment runbook's `--ignore-table` list and the harness, and, where PHP is installed, the harness's own functions are run (fingerprint vectors, and the lines it prints parsed by the script's own reader). The mutation matrix runs each test in a subshell and stops it at its first failed assertion, which cut the matrix's time by more than a third.

At the end of slice 2.2A the file has 191 tests and 169 guard mutants, all caught, and takes about 4m53s on the development machine (WSL2), against 162 tests, 130 mutants and 3m07s before the slice.

Slice 2.2B adds tests for the prepared-source record, the snapshot semantics, the restore, the sign-in and the re-upgrade, and 27 guard markers (the fake daemon gains the schema-object queries, the clearing statement and the sign-in and digest helpers). It leaves 206 tests and 196 guard mutants, all caught, and the full file takes about 10m55s on the same machine, against 4m53s after slice 2.2A. The growth is the number of worlds the new tests build (each stage test runs the real script several times) multiplied by the mutants they must catch; the matrix runs mutants one after another because they share the fake daemon's world.

**The dump check after L2.** The check counts every `INSERT` statement before it makes the table names unique and accepts both the layout `mariadb-dump` prints (the statement's first line ends at `VALUES`, the rows follow on their own lines) and the single-line form; any other form is refused as unrecognised (guard `G15-insert-format`). The fake daemon prints the observed layout. The file now has 207 tests and 197 guard mutants, all caught; the whole `./flow check repo` took 14m12s on the development machine. See L2, above, for how this was found.

**Slice 2.2C-1** adds 28 guards (22 in G20, 6 in G21) and the tests that catch each one's removal: 222 tests and 225 guard mutants, all caught (the whole file took 31m42s on the development machine; on the GitHub-hosted runner it takes about 39 minutes, which exceeded the CI job's 40-minute limit once the other gates were added, so that job's `timeout-minutes` is now 65). The first implementation had 26 guards; the independent review's two corrections (the `contact_methods` structure, the revocation event) added two guards, `G20-provenance-not-yet` and `G20-structure-contact-methods`, and strengthened the tests of `G20-structure-committed`, `G21-before-state`, `G21-after-state` and `G21-reversed`. The fake daemon answers the new fixed queries (ledger, stub read-back, row counts, schema parts, security digest, revocation counts) from one file each, so a test plants a single deviation. Lists the script holds (the 15 committed tables, as the 14 compared with the first upgrade and `contact_methods`; the stub; the 25 migrations; the durable row counts; the revoked ids and the event id) are pinned against the repository by `t_static_half_failed_lists`, and the two new harness actions against the script's reading of them by `t_static_the_new_helpers_agree`. Outside the fake daemon, the real failure and the structure of the committed tables were measured on MariaDB (`HalfFailedMigrationTest`: 6 tests, 100 assertions, including the half-failed versus fully upgraded `contact_methods` and the comparison's rejections), the harness helpers were run once, as a throwaway probe, against the dedicated upgrade *test* database (their output is exactly what the script requires), and the script's fixed SQL was run once against a real MariaDB 10.11.19 test database in the half-failed state (ledger, stub read-back and counts equal what the script expects); none of that touched the rehearsal environment.

**Slice 2.2C-2** adds 64 guards to this matrix (`G22-*`, above) and 70 in the PHP class that does the file work (`F-*`, run by `tests/Unit/Rehearsal/ResourceFileArchiveTest.php`, which has its own mutation matrix over a real directory and the real `tar`). The whole file now runs 249 tests and 289 mutants, all caught; a table-driven test runs only the case written for the removed guard while the matrix runs (`want_case`), which is what kept the added cost to about a quarter.

**The marker check.** The mutation matrix once reported "GUARD_TESTS lists G13-fixture-people, which has no marker in the script" on a CI run although the marker was there (the run's log shows `printf: write error: Broken pipe` on the line before it, and the matrix then mutated that very marker). The cause was the check `printf '%s\n' "${MARKERS[@]}" | grep -qx "$id"` under `set -o pipefail`: `grep -q` stops at its first match, the writer can then fail with EPIPE, and the pipeline reads as failed. It is now `registry_differences`, exact membership in two associative arrays with no pipeline, tested for a missing marker, an extra entry, prefixes, case and 40000 entries.

The fake daemon fails any call on request (so a failed listing can be tested), rejects an `exec` with no container, renders an absent label as `<no value>` and refuses to render a bind-mounted container, each as the real daemon does.

## Limits

- The fake daemon models the inspect fields the script uses. Those templates and the listing filters were also run against a real container, network and volume (read-only) when this slice was written. L1 then confirmed the remaining semantics against the real daemon, including Compose's behaviour with `--wait` on an internal network (`up` reached healthy).
- The image is pinned by tag, and the server version is checked separately. It is not pinned by digest.
- A stopped container that is attached to the rehearsal network does not appear in the network's `.Containers`, so the "foreign container attached" check cannot see it. Removing the network then does not harm that container (it only loses a network it could not start on), and a volume used by any container, stopped or not, is still seen and kept.
- The container inspect template cannot be rendered for a container with a bind mount (the real daemon errors). Such a container is treated as not the rehearsal database and kept.
- Cleanup checks the state directory before it removes anything, but an entry written by the same user in the instant after that check can still make the final `rmdir` fail. Cleanup then exits 1 with the marker already removed, so the directory is no longer recognised as the script's; the entry is left untouched and the directory has to be dealt with by hand. There is no automatic recovery from that exceptional condition.
- Slice 2.2 must send only fixed, validated SQL: the database allowlist (G6) constrains the `-D` argument, not the statements, and there is deliberately no SQL parser. `run` builds the complete Artisan argument vector itself (G11), so no caller-supplied option reaches a migration.
- The fake-daemon tests could not show the following, and L1 settled each on the real daemon (one run, one machine, Docker 29.9.2): the MariaDB 10.11.18 client supports `--sandbox`; the empty source volume is writable by uid 33; `SHOW GRANTS` prints `flc\\_rehearsal\\_app` with two backslashes, which the comparison accepts; the S2.1 inspect templates (`EPHEMERAL_FMT`, `ROLE_FMT`) render, and the runner's identity check passes against the daemon's real mount listing (the script handles a daemon that lists `tmpfs` mounts among `.Mounts` or not; L1 does not record which this one does). A different daemon version or platform is not covered.
- Not exercised live in L1: `migrate`, `migrate:status`, `release:show`, `relationships:check`, `resources:assets:prune` and the refusal paths (they are tested against the fake daemon only), and any cleanup that has to keep or refuse an object.
- **Host gateway residual.** `internal: true` withholds a route to external networks and publishes nothing, but Docker does not promise that a container on an internal network cannot reach a service listening on that network's bridge gateway address (the host side of the bridge). The rehearsal does not claim complete host isolation, and reading the network's IPAM configuration is not proof that host services are unreachable. What the design does guarantee: no port is published, there is no route to the internet or to other development networks, and the runner holds no credential but the synthetic application password. Whether a host service answers on the gateway is a fact about the machine. The owner accepted this residual for the synthetic rehearsal without measuring it: the optional connect test (L1 step 8) was deliberately omitted, so the gateway behaviour on this machine is **unmeasured**, not shown safe. It should be measured, with the owner's approval, before the rehearsal is given anything beyond synthetic data. No firewall or extra network infrastructure is added for it; a finding there is a decision for the owner.
- The runner and the preparation container share the development image, so the image's PHP settings (`zz-flow-dev.ini`) apply. Its `APP_KEY` and `APP_PREVIOUS_KEYS` are the run's synthetic keys (slice 2.2A), passed by name through the launcher; like the application password they are in the runner's environment while it exists, so `docker inspect` of a running runner shows them, and they protect nothing real.
- An interrupted credentials write can leave a `.compose.env.*` temporary file (mode 600) in the state directory; cleanup treats it as another entry (above), names it and keeps the directory until you remove it; `run.lock` is removed while held, which allows a negligible race; `stat -c` is GNU-specific.
- Identity labels and the run token guard against mistakes. They are not a defence against someone who can already create arbitrary Docker objects on the machine.

**Slice 2.2A limits.**

- **Settled by L2 (2026-11-14, one run):** the harness boots both applications in the runner on MariaDB, loads the fixture and reads `information_schema`; `mariadb-dump` as the application account takes both passes; loading the dump over the upgraded database leaves exactly the 18 newer tables (the check this slice built); the expected-upgrade digests match; and the stage timings are in the L2 table above. The audit's measurement of the foreign keys on the surviving tables was not repeated: L2 showed the tables remain, not their keys.
- **The prepared source's commits were not recorded in the volume** in this slice; slice 2.2B records them (see above) and every stage checks them.
- **The snapshot detects, it does not describe.** It is digests, so it says that a table changed, and which, not how.
- **Not the whole backup.** The dump is not compressed (the checksum is of the file that is loaded), the Resource files archive and its manifest are a separate record made by slice 2.2C-2 (not yet joined to the dump's manifest; run live only on its own, in L3b), and nothing here reconciles invitations or other security-sensitive changes after a restore.
- **A stage that stops part-way can leave the database partly changed** (a migration, a fixture, a load). The rehearsal is disposable: `cleanup`, then `up`, `prepare` and the stages again. A temporary `.dump.*` or `.<file>.*` file left by an interrupted write is another entry that keeps the state directory, as for `.compose.env.*`.
- The demonstration proves the defect with this fixture and these 34 tables. It does not prove that nothing else would differ in a different failure, such as a half-applied migration (slice 2.2C).

**Slice 2.2B limits.**

- **Settled by L2 (2026-11-14, one run):** `information_schema.tables`, `.triggers`, `.routines` and `.events` are readable by the application account and report what the stages expect; the one `DROP TABLE` statement (34 names, foreign keys off for its session) works through the restricted client; the dump loads as the application account; the structure digests (Laravel's schema introspection on MariaDB) are equal before and after a round trip through the dump; and the in-process HTTP sign-in works in the runner (read-only root, `session.driver=database`, trusted hosts from `APP_URL`). One run on one machine and one Docker version (29.9.3); another platform is not covered.
- **The sign-in is in-process.** It uses the application's kernel, middleware, cookies, CSRF check and database session, but not a socket, a web server or a browser, and it runs inside a transaction that is rolled back. It verifies the password step, the TOTP challenge and an authenticated `/me`, and that nothing persists afterwards. It does not independently verify commit-time behaviour or that a sign-in persists across separate transactions (for example an `afterCommit` callback, which a rolled-back transaction discards). The independent S2.2 review found no `afterCommit` use in the v0.3.0 application code, configuration or routes, and accepted this limitation for the recovery criterion.
- **The administrator's TOTP secret is derived from the run's key** and the previous key encrypts it, so the keyring is exercised for one enrolment; the other factors, and the recovery codes, are verified as restored rows (digests) and not used to sign in.
- **A docs-only commit after `prepare` needs a new `prepare`**, because the record names `HEAD`.
- **A stage that stops after the clearing leaves an empty database** (or a half-loaded one). The rehearsal is disposable: `cleanup`, then `up`, `prepare` and the stages again. There is no automatic recovery.
- The structure comparison covers columns, indexes and foreign keys as the engine reports them; it does not cover table options (engine, collation of the table), triggers or grants, which the schema check refuses or the dump does not carry.
