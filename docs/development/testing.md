# Testing

Strategy and rationale: [ADR 0014](../adr/0014-testing-and-database-compatibility-strategy.md).

## Commands

| Command | Runs |
| --- | --- |
| `./flow test` | Backend (Pest, MariaDB) and frontend (Vitest) |
| `./flow test backend [--pgsql] [pest args]` | Pest; `--pgsql` runs the same suite on PostgreSQL. Args pass through, e.g. `--filter=Health` |
| `./flow test frontend [vitest args]` | Vitest |
| `./flow test e2e` | Playwright journeys against the running stack (`./flow up` first) |
| `./flow check [repo\|backend\|frontend] [--pgsql]` | Everything CI runs (below) |

`./flow check` runs every check even after a failure, prints a summary, and exits non-zero if anything failed.

| Scope | Checks |
| --- | --- |
| repo | Compose config validates, shellcheck on `flow`/`scripts`, `./flow` CLI and `./flow release` behaviour tests (a real git fixture and the real artifact validator, with Composer/npm stubbed), actionlint on workflows, WordPress plugin PHP syntax |
| backend | `composer validate --strict`, Pint (`--test`), Larastan level `max`, Pest on MariaDB incl. architecture tests, (with `--pgsql`) Pest on PostgreSQL |
| frontend | `tsc -b` strict, ESLint, Prettier check, Vitest, production build, build verification |

## Backend

- **Pest** with Laravel's HTTP testing. Use Pest's function helpers (`getJson()`, `withHeaders()` from `Pest\Laravel`) rather than `$this->...`, so Larastan can type-check tests.
- **Feature tests** boot the app and run on a real database via `RefreshDatabase`, which migrates fresh on every run. That is how migrations are validated on both engines.
- **No SQLite.** `tests/TestCase.php` throws unless the driver is `mariadb` or `pgsql`, and unless the database name ends in `_test`. Tests run in `flowlife_test`, separate from your development database `flowlife`; `./flow` creates it.
- **Architecture tests** (`tests/Architecture`, see its README): module boundaries, Identity's layer rules, no HTTP clients outside `Infrastructure`, no `env()` outside config, no debug/dangerous functions, strict types, and a portability scan that bans MariaDB-only schema/SQL unless annotated `// portability-exception: ADR-NNNN`.
- **Authentication tests** use `Tests\Support\Console`, a browser stand-in with a cookie jar that starts every request from a clean session and guard, and that makes CSRF real: **Laravel skips CSRF entirely under PHPUnit** (it checks the app environment is `testing`), so a test that merely POSTs proves nothing about CSRF. Laravel's `json()` test helper also sends **no cookies** unless `withCredentials()` is set. Time-dependent tests move the clock with `Console::advance()`; the absolute-lifetime tests keep the user active (`advanceWhileActive`) so the 30-minute inactivity rule can never be what ends the session.
- **Multi-factor tests** (`tests/Feature/Modules/Identity/Mfa`, `tests/Unit/Modules/Identity`, `tests/Concurrency/MfaRaceTest.php`). `tests/Support/Totp.php` is an **independent implementation of RFC 4226/6238**, so the platform's TOTP adapter is checked against something that is not the library it wraps (and against the RFC's published vectors); `next()` hands out a code that has not been used before and moves the frozen clock a step when it must, because the platform accepts each time step once. `Tests\Support\Mfa` builds enrolled Accounts through a development-only fixture and signs in through the two real steps (`Console::loginWithMfa`). The suites cover enrolment (nothing is enrolled until a code is proved; the secret and codes are never retrievable and never in the audit trail), the challenge (password alone gives no session; expiry; five wrong codes; rate limits; a disable or a password replaced during the challenge, including in the same second), recovery codes (one use, hashing at rest), management (fresh proof; proof-before-switch), step-up (a test-only route behind `security.verified`), the policy (Access answers Identity's port; fail-closed default; a password-only session ended when Console access is granted), persistence on the real engine, and architecture rules (the TOTP library and the encrypter are used from one Infrastructure class each; the audit classes cannot name a secret; no role name in Identity; no QR-service URL, scanned over code and not comments).
- **MFA races** run across two real PHP processes like the credential ones, on both engines: a disabled Account and a replaced password each end a waiting challenge; two sign-ins spending one recovery code, and two presenting one authenticator code, cannot both succeed; and recovery-code consumption is pinned **on its own**, with no Account lock, because the sign-in race passes through the lock even if the atomic update is broken. Each scenario has a control that waits and then succeeds, so a passing test cannot be a refuse-everything test.
- **Mutation-check the security properties** as well: break one (drop the row lock, the credential binding, the proof before enrolment, the proof before a replacement switches, the step-up expiry, the encryption, the recovery-code hashing, replay protection, the atomic consumption; make the policy answer no) and watch a test go red. Two are layered on purpose: making consumption non-atomic is caught only by the direct test (the Account lock still protects the sign-in), and removing both layers fails four.
- **Authorization tests** set roles up with `Tests\Support\Access` (grant through the port; revoke and plant corrupt keys directly in the table), because the grant and revoke use cases do not exist yet. HTTP enforcement is tested on **test-only routes** registered inside the test (`can:console.access` and so on); no production endpoint exists to demonstrate it. Tests about the platform administrator derive the expected capabilities from the catalog (`Access::everyCapabilityId()`), so adding a capability changes only the deliberate "exact catalog" test.
- **Concurrency tests** (`tests/Concurrency`) prove the last-administrator invariant across two real PHP processes and two database connections. They commit real rows (so they sit outside `RefreshDatabase` and clean up after themselves, and refuse any database not named `*_test`). The test process runs a real use case and **pauses inside its open transaction**, after it has changed state and before it commits, by hooking the audit write. There it launches `tests/Concurrency/worker.php`, which runs a competing removal, waits for it to report READY, gives it a moment, and asserts it is **still blocked** (the lock) and then **refused with an active administrator still standing** (the re-check on committed state). Each scenario asserts both halves, since either alone can pass for the wrong reason. They run on whichever engine the suite targets (`./flow test backend [--pgsql]`), take about two seconds each, and rely on a fixed 1.5 s grace after the worker is ready, so a very slow machine could in principle make a broken lock look like a working one for that scenario; the deterministic query-order tests are the backstop. What they cannot show: a deadlock that needs a precise three-way interleaving. Lock ORDER is instead pinned by a deterministic test on the SQL actually issued.
- **Persistence tests** run against the real engine and assert refusals on real rows (a refused delete leaves the data in place). Use `Tests\Support\Identity::violation()` to run an operation the database must refuse: it wraps it in a savepoint, because on PostgreSQL a failed statement aborts the surrounding test transaction and every later query in that test would fail.
- **Mutation-check important database tests.** Because collations differ (MariaDB folds case, PostgreSQL does not), a test can pass on one engine for the wrong reason: removing canonicalisation leaves the MariaDB run green and fails only PostgreSQL. Run both engines, and break the property once to see the test go red.
- **OpenAPI contract test:** the routes under `/api/v1` and `openapi/openapi.yaml` must match exactly, and the health response must match its schema.
- **Prove a rule can fail.** When adding an architecture rule, plant a violation temporarily and confirm it goes red. (Pest passes an *array of subject namespaces* vacuously; use one subject per expectation.)

## PostgreSQL

`./flow test backend --pgsql` starts the `postgres` profile, creates `flowlife_test`, and runs the suite with the connection switched by environment variables (real environment beats `.env` and `phpunit.xml`, so only the engine changes). CI runs it on every push via `./flow check --pgsql`.

## Frontend

Vitest with Testing Library and jsdom. ESLint uses `typescript-eslint` `strictTypeChecked` (and forbids `console.*` in `src`, so nothing can log a credential by accident); TypeScript is strict with `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`. `npm run verify:build` confirms the Tailwind utilities the Console really uses are in the built CSS (its needles are built at run time, because Tailwind scans that script too and a literal class name there would generate itself).

- **Authentication tests replace `fetch`, not modules.** `src/test/fakeApi.ts` stands in for the Platform API at the network boundary, so the real HTTP client, `AuthProvider`, router and pages all run together; an unexpected request fails the test, every call is recorded (to prove where a credential was and was not sent), and `withSession` gives `/login`, `/me` and `/logout` one consistent server-side session. Screens are driven with `userEvent`, and located by role and label, the way a person (or a screen reader) finds them.
- **What they cover:** resolving who is signed in (loading, authenticated, unauthenticated, and API-unreachable, which is *not* signed out), Console entry by capability and the access-denied page, sign-in (one message for every refusal, the login reply not trusted over `/me`, rate limiting, return path), sign-out, an ended session, no polling (fake timers installed before render, so any timer the app starts is one the test controls), forgot / reset / accept / change (including that enumeration-safe answers are identical whatever the server says), fragment scrubbing against the real `window.history` (`replaceState` used, no entry added), and that credentials never reach storage, logs, URLs or the screen.
- **Source rules (`src/guardrails.test.ts`)** for the risks that running one path cannot show: system role names, browser storage, cookie writes, `fetch` outside the API layer, absolute URLs, `credentials: 'include'`, a configurable API origin, raw HTML injection. Each rule has a positive control (the scanner is run over synthetic offending code and must flag it) and a negative one, and the scan asserts it looked at the real source.
- **Mutation-check the security properties** here too: break one (stop scrubbing the fragment, poll in the background, drop the capability check, trust the login reply, write to storage) and watch a test go red. Some properties are layered on purpose: the return-path guard has three independent defences, so removing one leaves the tests green, and only removing all three fails them.

## E2E

`e2e/auth.spec.ts` drives real Chromium through the gateway for session authentication: the exact production cookie is accepted and returned on plain-HTTP localhost, sign-in with the CSRF token regenerates the session, sign-out works, wrong-password and unknown-address are indistinguishable, and a page on a *different site* can neither sign the user out (a real cross-site POST) nor read the API (no CORS). `./flow test e2e` first seeds a development-only fixture account. A Playwright smoke test (`apps/guardian-console/e2e/smoke.spec.ts`) loads the Console in Chromium (nobody is signed in, so it is the login page), checks a Tailwind computed style, and checks its first API call goes to the page's own origin; the signed-in landing page and the API health it shows (gateway, Vite, Laravel and MariaDB together) are checked in `console.spec.ts`. A small `gateway.spec.ts` pins the single-origin routing: `/api` and `/up` reach Laravel, unknown API paths are JSON rather than the Console, client-side routes still boot the Console (an unknown visitor lands on its login page) and its public pages open by deep link, the HMR websocket connects through the gateway, and the retired hosts are refused. `e2e/credentials.spec.ts` is one serial journey through the credential lifecycle in real Chromium, with real Mailpit mail: an invitation is accepted (the invitee is *not* signed in, a replayed token answers like a garbage one), the invitee signs in, changes their password (this session survives but is rotated, another browser's session ends, and the old session id is dead, measured by replaying the copied cookie), and a forgotten password is recovered from the emailed link (the reset ends every session). Its accounts are reset on every run by the seeder. `e2e/console.spec.ts` drives the Console's own screens in the same real Chromium, by clicking and typing: an unauthenticated visitor is sent to sign in, keyboard-only sign-in returns them to the page they were headed for, a refresh keeps the session, sign-out ends it (the back button does not bring the Console back and a copied cookie no longer works), a wrong password and an unknown address get one sentence, an ended session sends them back with a message, an Account without Console access sees the access-denied page (not the login page), an invitation is accepted by typed token and by link (no session is created, and the chosen password then signs in), a forgotten password is recovered from real Mailpit mail (the link's fragment is scrubbed from the address bar and history, the reset ends the other session, the old password is dead), and a password is changed while signed in (a wrong current password changes nothing; success keeps the session, rotated and re-dated, and kills the copied cookie and the old password). It also checks that nothing secret reached browser storage or the browser console. Raw API calls appear only to measure what the platform now holds. `e2e/support.ts` holds the helpers it shares with `credentials.spec.ts`, which measures the platform directly and so starts its pages on Laravel's stateless `/up` rather than the Console (the Console asks who is signed in as it loads, which issues an anonymous session cookie). **Sign-in budget:** every attempt, refused or not, counts against a per-address login limit (`identity.login_throttle`, 30 per 15 minutes by default) and a whole run makes about 45 (the administration journeys add only the few that are about signing in), so the **development stack raises it** (`IDENTITY_LOGIN_MAX_ATTEMPTS_PER_IP=200` in `.env.example`; production keeps the default and reads no such variable) and `./flow test e2e` **refuses to run** unless it is at least 100. It also clears the counters first.

`e2e/mfa.spec.ts` covers two-step verification in the same real Chromium: a later sign-in (password, then a code; a wrong code is one sentence), a recovery code (typed as printed, works once, the same code fails next time, the count goes down), managing it (regenerate codes on fresh proof with a recovery code, replace the authenticator with proof-before-switch, the old authenticator and old codes then fail), and a pending sign-in that cannot finish after the password it proved was changed on another session. The first-time enrolment journey (QR code and manual key, a wrong code enrols nothing, recovery codes shown once behind an acknowledgement, a reload cannot bring them back) is the invitation journey in `console.spec.ts`. The browser cannot see an authenticator app, so the accounts are **enrolled development fixtures with a known secret and known recovery codes**, and the journeys compute codes with an RFC 6238 implementation in `e2e/support.ts` (independent of the platform's). The platform accepts each authenticator time step once, so **each journey has its own account and secret** (parallel workers must not share one). Every journey also checks that nothing secret reached browser storage or the browser console. **The whole suite is self-contained: it never reaches a public service.** The one outbound dependency, the breached-password check, runs as the no-op checker in development and CI (`.env.example` sets `IDENTITY_COMPROMISED_PASSWORD_CHECK=none`), and `./flow test e2e` **refuses to run** if the platform resolves anything else. What the platform does when a password is breached, or the service fails, is proved in the backend tests against a faked service (`BreachCheckEndpointsTest`, which puts the real adapter behind each endpoint that sets a password). `e2e/administration.spec.ts` covers operator administration (ADR 0024): an administrator opens Account administration and a guardian is refused (on the page, and at the API without being asked to prove anything); a sensitive action from a session whose last proof is older than 15 minutes is refused, the Console prompts, a wrong proof is refused, the right one closes the prompt with **nothing done**, and only a deliberate second press acts; an operator is invited, the emailed link (token in the fragment) is followed, the invitee accepts (email **verified**), enrols and enters the Console; their access is removed and restored and takes effect on their next request; they are disabled (session ended, sign-in refused) and re-enabled (still challenged for a second factor); and another person's second factor is reset (old code and recovery code refused, a new authenticator enrolled first). **These journeys start from sessions the platform mints** (`E2eSessionSeeder`, run by `./flow test e2e` after the account seeder): it drives the platform's own `POST /login` and `POST /mfa/challenge` in-process with a known Account and a single-use recovery code, so no journey spends a password-and-second-factor login from the public rate budget on set-up, and sign-in is still done for real wherever it is the subject. Some are minted with a proof older than 15 minutes (the clock is moved back for the sign-in and the activity time restored), so the platform judges them exactly as it would a real expiry, with no waiting. Chromium will not have a Secure `__Host-` cookie injected for an http address but accepts it for the same host addressed as https, which is how `signedInAs` installs them. The seam is local and testing only, is not part of the default seeder, is referenced by nothing in the application, and writes to a git-ignored file (`apps/guardian-console/e2e/.fixtures/`); backend tests pin each. `./flow test e2e` also migrates the development database first, so a new migration cannot make the seed fail. Both run in the Playwright container on the `e2e` profile. In CI it is a **manually triggered** workflow to save minutes. Do not grow it into a large suite yet.

## The CLI's own tests

`scripts/tests/cli.sh` covers `./flow` dispatch and the `./flow ci` contract. It stubs `gh` on `PATH`, so it asserts which `gh` command each subcommand delegates to — plus the guards — without needing the GitHub CLI, credentials or network. It also asserts two architectural properties: that `require_gh` is referenced only by `scripts/commands/ci.sh`, and that `ci.sh` depends on neither Docker nor a set-up environment.

## CI

`.github/workflows/ci.yml` runs on pushes to `main`, on pull requests (docs-only changes are skipped), and on manual dispatch, cancels superseded runs on the same ref, uses Linux runners, caches the PHP image layers, and runs `./flow setup --skip-build` then `./flow check --pgsql`. See also [Docker environment](docker.md#ci-parity). No deployment happens from CI.

## Triggering and reviewing CI

`./flow ci` is a deliberately thin wrapper over the [GitHub CLI](https://cli.github.com) for this project's two workflows. It is **not** a general GitHub client: authentication, remotes, secrets, artifacts and dispatching arbitrary workflows stay plain `git`/`gh` commands.

**`gh` is required only by `./flow ci`.** Every other `./flow` command works without it, and `./flow check --pgsql` remains the provider-independent local equivalent of the CI checks.

```bash
sudo apt install gh            # Debian/Ubuntu; or pacman -S github-cli on Arch
gh auth login -s workflow      # the 'workflow' scope lets you push .github/workflows changes
```

| Command | Does |
| --- | --- |
| `./flow ci run [--ref REF]` | Triggers the CI workflow (default ref: current branch) |
| `./flow ci e2e [--ref REF]` | Triggers the E2E smoke workflow |
| `./flow ci status [--limit N]` | Recent runs of both workflows |
| `./flow ci watch [RUN_ID]` | Follows a run to completion; exits non-zero if it fails |
| `./flow ci logs [RUN_ID] [--full]` | Failed steps when the run failed, otherwise the whole log |
| `./flow ci rerun [RUN_ID] [--failed]` | Re-runs a run, or only its failed jobs |

Run ids are optional and default to the most recent run, so `./flow ci run` then `./flow ci watch` is the normal loop.

A manual run needs `workflow_dispatch` on the **default branch**, so a newly added or edited workflow must be pushed before `./flow ci run` will accept it.

**Before making the `./flow check` job a required status check (branch protection): revisit `paths-ignore`.** The workflow currently skips docs-only changes (`docs/**`, `**/*.md`) to save minutes. A workflow skipped by path filters never reports a status, so a *required* check would stay "pending" forever and block docs-only pull requests. Either remove `paths-ignore` (and accept the minutes), or add an always-running lightweight job/ruleset that satisfies the requirement. `workflow_dispatch` lets you run CI by hand on a docs-only commit, but a dispatched run does not satisfy a required check on a pull request.

## Live, network-dependent smoke test (manual)

`tests/Live` checks the real Pwned Passwords service: that it answers in the format the adapter parses and that adapter and service agree on a known breached password. It is in **no test suite**, so `./flow test`, `./flow check`, CI and e2e never run it and never need the public network. Run it by hand, for example after changing the adapter or if the service is suspected to have changed:

```bash
./flow test backend -- tests/Live
```

With no outbound network it **skips**, saying so, rather than failing: an offline machine is not a regression. It fails only when the service answered and the answer was wrong. Do not add other live tests here without the same care; this is not a framework for external services.

## Production hardening (Phase 9)

- **The stale-authentication races** (`tests/Concurrency/StaleAuthenticationRaceTest.php`) reproduce the exact window [ADR 0024](../adr/0024-privileged-operator-administration.md) recorded and [ADR 0025](../adr/0025-account-security-generation.md) closes, on both engines, with the same two-process harness as the other races: the proof pauses inside its transaction, a second process runs a security-invalidating operation and blocks on the Account lock, the proof commits, the operation commits **finding no session row to delete**, and only then does the test do what the transport does. TOTP completion, recovery-code completion, disable and password reset, each with a control that succeeds when nothing supersedes the proof, plus the reverse ordering. Removing either enforcement point — the check in `ConsoleSession::establish` or the `EnforceSecurityGeneration` middleware — makes them red; that was verified by doing it.
- **The deterministic proofs** (`tests/Feature/Modules/Identity/Auth/SecurityGenerationTest.php`) pin which operations advance the generation and which deliberately do not, that a session is bound to what its proof was checked against, that a superseded session is refused on its very next request and destroyed, that a session holding no generation or a non-integer one fails safe, that a password change and an authenticator replacement keep the caller signed in, and the middleware's position before authentication. One of them measures a framework behaviour the design leans on: Laravel's database session handler does **not** resurrect a row deleted mid-request.
- **Session maintenance** (`tests/Feature/Modules/Identity/SessionMaintenanceTest.php`) pairs what must go with what must stay for every case, including a live signed-in session surviving a sweep, a backlog larger than one delete batch, and the explicit retention decisions (the audit trail and invitations are never touched).
- **Key rotation** (`tests/Feature/Modules/Identity/Mfa/KeyRotationTest.php`) proves the [runbook's](../runbooks/app-key-rotation.md) claims rather than restating them, including that an unreadable secret is reported as a fault and never as a wrong code. Each case builds its own keys; the development key is never rotated.
- **The browser security policy** has two halves, in two places, because they answer different questions. `tests/Feature/Modules/Security/BrowserSecurityPolicyTest.php` pins the policy and that both deployment adapters are generated from it; a CSP that *breaks the Console* passes every assertion in that file. `apps/guardian-console/e2e/security.spec.ts` is the half that matters: real Chromium, against the real production build, on the gateway's production-equivalent origin, showing both that nothing breaks (zero `securitypolicyviolation` events across startup, sign-in, MFA, QR display, administration, API calls, recovery-code copy and download, and fragment scrubbing) **and that the policy actually blocks** a cross-origin script, an inline script, a cross-origin image, a cross-origin fetch and being framed. `eval` is deliberately not probed: Playwright's `page.evaluate` runs through the debugging protocol, which is not subject to the page's CSP, so the probe would prove nothing while looking as though it had.
- **Production configuration** (`tests/Feature/Modules/Security/ProductionReadinessTest.php`) is mostly tested by *failing*: a check that always passes is worse than no check, because it is believed. It is deliberately not exhaustive — asserting that each of twenty-six checks reads the setting it names would be twenty-six restatements of the implementation.
- **Schema indexes** (`tests/Feature/Modules/Identity/SchemaIndexTest.php`) pin the indexes the review found sufficient, with EXPLAIN on both engines, and state the one query that is deliberately a scan together with the scale at which that stops being true. The prune's plan is measured on two thousand rows, because both engines correctly scan a tiny table and asserting the plan on an empty one would prove only that the planner can count.
- **`./flow audit`** is deliberately outside `./flow check`: advisory databases change without a commit and need the network, and the gate must stay deterministic and offline. A CLI test asserts the gate does not reach one. See [dependencies](../security/dependencies.md).
